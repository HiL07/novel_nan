# 素材流程：从一本小说到素材库

> 相关代码：`python-service/app/material_facts.py`（读原文 / 整理卡片）、`app/extractor.py`、`app/extract_checkpoint.py`；
> Java `NovelExtractService`、`MaterialCompileService`、`MaterialService.createCandidates`；前端 `views/novel/extract.vue`。

## 1. 分步，而不是一次跑完

```
① 小说提取（只读原文）  → 实体档案（实体 + 核实过的事实）+ 章节摘要       可查看、可删实体
② 整理卡片（单独发起）  → 素材卡 / 体系卡 / 剧情段 → 「待确认」          逐条确认
③ 用户确认             → 素材库
④ 精炼合并（素材库上）  → 跨书 / 同书相似素材 → 主条目 + 可选版本         逐组确认（见 精炼合并.md）
```

为什么拆开：

- **每步结果都能先看、先改**：读完先看实体档案，把认错的路人、无关的东西删掉，再花时间整理。
- **出错只重做那一步**：卡片整理得不好，可以换个模型重新整理，不用把全书重读一遍（GGUF 读一遍全本要十几个小时）。
- **每步可以用不同的模型**：读原文用本地 GGUF（免费、慢），整理卡片可以用 DeepSeek（输入很短，一本书约 1 元）。

旧版做法（每段直接挑几条素材、一句话概括）已经去掉，原因是：每段各提各的看不到上下文，一个场景就成一条素材；
「一句话、用自己的话概括」让模型丢掉了具体细节；同名合并时后面章节补充的属性被直接丢弃。

## 2. 读原文：记实体和事实（`scan`）

### 分章（`text_loader.split_book`，2026-11-02 改）

逐行判断标题（`detect_heading`），Java `ChapterCounter` 用同一套规则数章数（两边一起改；改了规则就换
`FileService.CHAPTER_RULES_MARK` 的版本号，启动时会把所有 txt / md 重数一遍）。

- **章级**「第X章 / 回 / 节 / 话」（数字和「第」「章」之间可以有空格，如「第 9章」「第二 章」）、「Chapter N」；
  **卷级**「第X卷 / 集 / 部 / 篇」「卷X」「上部　面壁者」；**特殊**序章 / 楔子 / 尾声 / 番外…。可带「正文 / 正文卷 / VIP章节」前缀。
- **像正文的不算标题**：编号后先分隔（空格、冒号…）再写的都算标题。没有分隔时，章级只在带「。」或以英文句点结尾时算正文；
  卷级 / 特殊标题带任何标点就算正文（「第一部分为灵性，第二部分为魂性。」「第一篇论文就是这个？！」）。
  EasyWriting 的「没分隔就接逗号 / 问号 = 正文」在真实书里会误杀「第97章你他娘是个流民？」「第十章杀！」这类真标题，所以章级放宽。
- 卷名后面带着章号的（「第二十七卷红色星期五第十六章…」，下载站常把卷 + 章写在一行）算章。
- 书里有章级标题时，**卷标题只断开**：卷下正文 ≥200 字（卷简介，或《三体》二三部这种只有「上部 / 第一部」的整卷）保留为一个单元（`kind: volume`），
  否则丢掉；之后各章带 `volume`。没有章级标题时，卷标题当章。都没有时用「1.标题 / 一、标题」兜底（至少 3 处）。
- 首个标题前 ≥1500 字的成为「开篇」（`kind: opening`），不到的是书头（书名 / 作者 / 简介），存进结果的 `preface`，不读。原来是 ≥50 字就单独成「序/前言」。
- 只有标题没正文的跳过；紧跟同名标题的（下载站重复章名）不计入警告。完全没有标题、又超过 5000 字时按段落分成约 5000 字一段（「第 N 段」，`kind: segment`）。
- 警告进结果的 `splitWarnings`：跳过的空标题数、超过 1/3 的章不到 200 字、按字数分了段。
- 训练（`local/dataset.py`）用 `segment=False`，没有标题时仍整篇一组，书头也作为一组样本。
- 实测（`data/upload/` 40 本，`scripts/split_compare.py`）：31 本章数不变；1 本旧规则只认出 21 章（「第二 章」「第 9章」带空格）→ 744 章；
  其余差 1–3 章，都是去掉了误判的正文行（「第三章的剧情，则开始回收…。」）或下载站的残缺重复标题（「第116章。」）；Java 与 Python 章数 40/40 一致。

### 逐章读（`chapter_scan.scan`，2026-11-02 起；设计见 `docs/素材提取改造方案.md` §3.0 / §3.0.2）

原来是「3000 字一块、短章合并、并发读、读两遍」。现在参照 EasyWriting 的拆书改成**一章一次调用、严格按章节顺序串行**：

- **读取单位**：一章一份，短章也不合并。超过上限的超长章按段落切成几份（`chapter_jobs`），按顺序读，最后由代码合成一章（`merge_parts`：
  事件 / 爽点等拼接，open 钩子取第一份、end 钩子取最后一份，情绪的 open / close 取首尾、peak 取爽点最强那份）。
  上限：大模型 2 万字（`API_MAX_CHARS`）；GGUF（本机服务）= 分段字数 × 2（默认 6000，GGUF 上下文建议 ≥ 12288）；
  应用内本地模型 = 分段字数（上下文窗口小）。
- **滚动上下文**（每章 prompt 里由代码挑）：上一章 / 上一份的一句话（≤2 条）、本章原文里出现了名字 / 别名的已知实体（≤15 个，各带 4 条已知事实，
  只让模型补新事实）、主角名 + 当前状态（各字段最新的变化）、未回收的伏笔 / 悬念 / 承诺（≤20 条，关键词出现在本章原文的优先，其余按最近埋下）。
  伏笔 plant 由代码编号 `T<n>`，advance / payoff 必须引用列表里的编号——所以读一遍就能串上伏笔，不再需要第二遍。
- **大模型也不并发**（滚动上下文要按顺序）。DeepSeek 实测（2026-11-02，5 章 1.04 万字，标准档）：47 秒、5 次调用、输入 1.44 万 / 输出 0.89 万 token，
  每章都有一句话和章末钩子，9 条爽点摘抄全部对上原文，99 条事实全部核实。
- **档位** `materials.depth`：`fast` = 实体 + 事实、一句话、事件；`standard`（默认）再加钩子、爽点、伏笔、本章功能、情绪、主角变化、关系变化、
  设定动态、金句，前 3 章加黄金三章深拆；`deep` 再加情节节点（正文按段落编号 `[n]` 给模型，代码把段号区间修成按顺序不重叠，换算成本章字符区间）。
  每章输出上限：fast 1500 / 1000，standard 3000 / 2000，deep 3600 / 2400（大模型 / 本地）。字段顺序 = 实体在前，截断时先丢后面的次要项。
- **核对**：事实对不上原文的进实体的 `unverified`（每个实体 ≤10 条，整理卡片不用）；钩子 / 爽点 / 伏笔 / 主角变化 / 关系 / 设定动态对不上时条目保留、
  quote 清空、`verified: false`；金句必须逐字（规范化后子串，不接受三元组近似）对上，否则丢掉。通过的都记 `at` = 在本章原文里的偏移（原文高亮用）。
  枚举外的值（钩子 / 爽点类型等）整条丢掉，强度截到 1–3。
- **失败**：某章失败记一行 `failed` 继续下一章；整本读完后失败的章再试一次（仍失败标 `retried`，续跑不再重试）；连续 5 章失败就停下（任务转「已中断」，可继续）。
- **断点**：`pass1` 每章（或每份）一行，key = `ci` / `ci:part`，行里有实体、章节卡、伏笔操作（plant 的编号在写断点前就分配好）。
  续跑时按顺序重放这些行，重建实体档案、伏笔表、主角状态，再从第一个没读的章接着读。指纹含 `mode: serial-v1`、`cardsV`、档位、上限，旧的分块断点会作废重读。
- **第 2 遍**（`rounds: 2`，默认改为 1 遍）：再按顺序读一遍，带全书已知实体，只补漏掉的事实和实体（`pass2`，旧的 `scan_prompt`），不再做章节卡。
- **代码统计**（不花 token）：每章字数、段落数、平均段长、对白比例、出现的已知实体（一个正则扫全部名字 / 别名）、本章首次出现的实体数。
- **结果**：`chapterCards[ci]`（status done / failed / empty + 章节卡字段 + `stats`）、`threads`（`T<n>`：埋于、推进、回收、状态）、`lead`、
  `pacing`（`breakdown.pacing`：爽点密度、章末钩子率、最长无爽点区间、类型分布、伏笔回收距离、主角成长线、文风）；
  `chapters[i].summary` = 一句话 + 前 3 个事件（剧情段、角色卡等下游照旧读它），`characters` = 本章出现的角色实体，`events` = 章节卡的事件。
- **章节范围**（`materials.fromChapter / toChapter`，从 1 数，to = 0 读到最后）：提取对话框先调分章预览（`split-preview`，和提取同一套分章）选范围，
  可以先拆前几章看效果。只读范围内的章：结果的 `chapters` / `chapterCards` 只含这几章（`ci` 从范围起点数），`range {from, to, total, chars}` 记全书位置；
  黄金三章按全书前 3 个正文章算（范围不含它们就不做）。断点指纹含起点、不含终点。
- **逐章查看**（提取中也能看）：每读完一章，`pass1` 就多一行；`chapter_scan.live(key, since)` 把 since 之后变化的章整章重算（超长章几份合成一张卡）返回，
  另带 `chapters.json`（范围内的章节列表）和内存里的「正在读第几章」。前端提取工作区（`views/novel/extractWorkspace.vue` + `components/material/extractLive.js`）每 3 秒增量拉取，默认跟随最新读完的章；
  中间显示原文（按需取，全书下标），核实过的摘抄按 `at` 在附近精确查找后高亮（钩子 / 爽点 / 伏笔 / 人物 / 设定动态 / 事实分色），深拆档的情节节点给段落加底色；
  点右边条目原文滚过去，点原文高亮右边对应条目高亮。提取成功后用结果里的数据看同一个界面。
- 自测：`scratchpad` 里的离线脚本用假模型覆盖了切分合并、枚举、偏移、伏笔串联、失败重试、断点续跑；评测 `scripts/extract_eval.py --depth … [--no-compile]`
  额外打印章节卡指标（有一句话 / 章末钩子的章数、爽点每章数与核实率、伏笔埋 / 收、主角变化 / 关系 / 设定动态 / 金句数、失败章）。

### 原文依据核对（代码做，不靠模型自查）

小模型最大的问题是「脑补」，所以每条事实的 `quote` 都由代码去原文里找（`Source.locate`）：

1. 原文和摘抄都去掉空白和标点，摘抄短于 4 个字的直接不算；
2. 摘抄是原文的子串 → 通过；
3. 否则把摘抄切成字符三元组，≥60% 能在原文里找到 → 通过；
4. 不通过的事实不算已核实（`factsUnverified`），保留在实体的 `unverified` 里。
### 聚合（代码，不用模型）

- 同分类 + 规范化名称（去空白和标点、小写）或任一别名相同 → 同一个实体；
- 事实按字符二元组重合去重（较短那条 ≥60% 出现在已有事实里就算重复），每个实体最多保留 80 条；
- 结果按事实数从多到少排序，存进提取结果的 `entities`（每条事实带章节标题和章节下标 `ci`）。

### 截断修复

输出被 `max_tokens` 截断时，退回到最后一个完整的 `}` 并补齐括号再解析（`_close_truncated`），前面写完的实体不丢。

## 3. 整理卡片（`compile_cards`）

输入只有实体档案和章节摘要（很短），所以可以换模型、换范围多次整理。

- **素材卡**：事实 ≥2 条的实体每个一次调用；只有 1 条事实的同分类 5 个一批。输出：
  `useful`、名称、细分类型、一句话概括、100–300 字详细描述、按分类模板填的属性、「作者用法」（原作怎么用它制造冲突）、
  「借用提示」（借到别的小说时哪些可直接用、哪些要改）、标签、**量级** `tier`（1–5，见下）。
  - 代码另算 `bookPos`：这条实体最早一条事实所在章 ÷ 原书总章数（0–1）。
  - 提示词：只依据给出的事实，不编造、不补充原因或来历，没依据的属性直接省略。
  - `useful: false`（只有空泛情绪或一次性动作）不进候选箱，计入 `notUseful`。
  - 属性值是「无 / 未提及 / 无明确信息」这类空话的，代码直接丢掉（`_EMPTY_VALUE`）。
- **体系卡**：同一本书里同一细分类型的世界观卡 ≥3 张时，再合成一张「XX 体系」：组成、层级与顺序、核心规则、代价、限制。
- **剧情段**：章节摘要每 20 章一个窗口（相邻窗口重叠 3 章），找跨章的完整剧情段，抽象成骨架：起因 / 冲突 / 转折 / 结果 / 功能
  （开局、打脸、升级、反转、救场、揭秘…），人物用「主角 / 对手 / 甲 / 乙」代称，不留原作专有名词。
  同名或章节范围重叠 >50% 且功能相同的只留一个。

分类属性模板：

| 分类 | 属性 |
|---|---|
| 怪物 | 外形、能力、弱点及原因、习性、社会结构、来源、与人类的关系 |
| 世界观 | 规则内容、代价、限制、谁能打破、对社会的影响 |
| 物品功法 | 作用、代价、获取方式、限制 |
| 角色 | 人设核心、反差、能力、动机、关系、名场面 |
| 势力 | 结构、目标、资源、内部矛盾 |
| 地点 | 特征、危险、特殊规则、产出 |
| 情节 | 起因、冲突、转折、结果、功能 |

结果进入「待确认」候选（`material_candidate`）。同一本书已有的同分类同名候选或素材自动跳过。
保存成素材时，`tier` / `bookPos` 写进 `material.profile`。

### 量级（`material.profile`）

素材本身只记「它是什么」，没有「它有多强」。灵感墙在开篇时检出一堆神明，就是因为检索分不出山匪和古神。
所以每条素材多一个跨书通用的量级，按影响范围算，不用各书自己的境界名：

| 量级 | 含义 |
|---|---|
| 1 | 个人 / 街头：一个人、一伙山匪、一头野兽 |
| 2 | 地方：村镇、小门派、一片山林的妖王 |
| 3 | 一国 / 大宗门：王朝、大宗门、一方霸主 |
| 4 | 大陆 / 天下：魔族大军、天下第一宗、灭世级灾兽 |
| 5 | 神明 / 世界之外：神、天道、上古存在 |

- 来源：整理卡片时顺带输出；已有素材在素材库「量级 · 补全」批量标注（`MaterialProfileService`，Python `material_profile.label`）：
  - 每 20 条一次调用，大模型或 GGUF；代码只收本批序号、1–5 的整数，其他丢掉；
  - 后台单批、可暂停，每批标完立即写库；拿不准时提示词要求取低的一级；
  - 同一次任务先用代码补 `bookPos`（读提取结果的章节列表，把事实的章节标题换成章号）。
- 作者在素材编辑里改量级 → `tierBy = user`，之后的批量标注（包括「AI 标过的也重标」）都不覆盖。
- `bookPos` 是弱信号（很多神明在楔子里就以传说出场），只在没有量级时兜底。

## 4. 断点续跑与任务状态

长篇小说用 GGUF 要跑十几个小时，必须能断开后接着做。

### 断点

`data/extract-cache/<key>/`：

- `meta.json`：指纹。提取用 文件 / 字数 / 分块字数 / 块数 / 遍数 / 分类 / 特别关注；整理卡片用 实体键和事实数的哈希 / 是否整理剧情段 / 章节数。指纹变了（换了参数）就清空重来，避免把不同切法的结果拼在一起。
- `pass1.jsonl` / `pass2.jsonl` / `chunks.jsonl`（不记实体时的章节分析）/ `cards.jsonl` / `systems.jsonl` / `arcs.jsonl`：每读完一块、整理完一批卡就追加一行并 fsync；最后一行写到一半被打断时读取跳过。
- 断点键：提取 `e<任务 id>`，整理卡片 `k<任务 id>`。结果保存成功后删除断点。

### 状态

| 状态 | 什么时候 | 能做什么 |
|---|---|---|
| 排队中 / 运行中 | 刚提交 / 正在跑 | 暂停、取消 |
| **已中断** | 服务重启、AI 服务不可达、模型出错、用户暂停 | 继续（从断点接着做）、取消 |
| 成功 | 跑完并保存结果 | 查看（提取任务不能删） |
| 失败 | 只有用户点「取消」才会到这里 | 查看、删除（连同断点） |

「继续」时如果 Python 里同一个任务还在跑（只是 Java 重启了），直接接着轮询它，不重复提交；Python 也会拒绝在仍被占用的断点键上再起一个任务。

## 5. 实测（本地 GGUF）

机器：RTX 4060 Laptop 8GB；模型：Qwen3-4B-Instruct-2507 Q4_K_M（llama.cpp）；样本：《耐瑟瑞尔的辉煌》前 6 章，13,609 字。

| | 读 1 遍 | 读 2 遍 |
|---|---|---|
| 总耗时（含整理卡片） | 574 秒 | 971 秒 |
| 实体数 | 19 | 25 |
| 核实通过 / 丢弃的事实 | 46 / 0 | 119 / 13 |
| 实体召回（以 2 遍的名称和别名为基准） | 12 / 27 | 27 / 27 |

折算：每遍每千字约 **16 秒**，整理一张卡约 **18 秒**。313 万字的全本读一遍约 14 小时，所以分步、暂停和继续很重要。
整理卡片改用大模型能省掉卡片那部分时间。对照：旧版一次提取全本用 DeepSeek 花了约 12 元，而且约 40% 的输出花在被丢弃的候选上。

评测脚本：`python-service/scripts/extract_eval.py`（同一段样本比较不同模型 / 遍数的耗时、token、核实率、实体召回，并排展示卡片）。
