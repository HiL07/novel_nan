# 素材流程：从一本小说到素材库

> 相关代码：`python-service/app/material_facts.py`（读原文 / 整理卡片）、`app/extractor.py`、`app/extract_checkpoint.py`；
> Java `NovelExtractService`、`MaterialCompileService`、`MaterialService.createCandidates`；前端 `views/novel/extract.vue`。

## 1. 分步，而不是一次跑完

```
① 小说提取（只读原文）  → 实体档案（实体 + 核实过的事实）+ 章节摘要       可查看、可删实体
② 整理卡片（单独发起）  → 素材卡 / 体系卡 / 剧情段 → 「待确认」          逐条确认
③ 用户确认             → 素材库
④ 精炼合并（素材库上）  → 跨书 / 同书相似素材 → 主条目 + 可选版本         逐组确认（见 精炼合并.md）
```

为什么拆开：

- **每步结果都能先看、先改**：读完先看实体档案，把认错的路人、无关的东西删掉，再花时间整理。
- **出错只重做那一步**：卡片整理得不好，可以换个模型重新整理，不用把全书重读一遍（GGUF 读一遍全本要十几个小时）。
- **每步可以用不同的模型**：读原文用本地 GGUF（免费、慢），整理卡片可以用 DeepSeek（输入很短，一本书约 1 元）。

旧版做法（每段直接挑几条素材、一句话概括）已经去掉，原因是：每段各提各的看不到上下文，一个场景就成一条素材；
「一句话、用自己的话概括」让模型丢掉了具体细节；同名合并时后面章节补充的属性被直接丢弃。

## 2. 读原文：记实体和事实（`scan`）

### 分块

- 默认每块 3000 字（可调 1500–6000）。小块召回更高、块数更多。
- 短于 1500 字的章节和相邻章节合成一块，每章前面加「【章节标题】」，方便定位。
- 长章节按段落边界切块（`text_loader.split_chunks`）。

### 每块一次调用

模型输出：

```json
{"summary": "本段剧情摘要，≤80 字",
 "entities": [{"category": "monster", "name": "狼人", "aliases": ["狼族"],
               "facts": [{"fact": "月圆强制变身", "quote": "每逢满月就会被迫变身"}]}]}
```

提示词要求：只记录原文明确写出的、具体到能直接用来写作的内容（外形、能力、弱点、规则、代价、习性、来历、限制）；
普通路人、一次性动作、纯情绪不记；每条事实附 ≤30 字的原文摘抄。分类有 世界观 / 势力 / 角色 / 怪物 / 地点 / 物品功法，
不含情节（剧情段在整理卡片时从章节摘要里找）。

### 原文依据核对（代码做，不靠模型自查）

小模型最大的问题是「脑补」，所以每条事实的 `quote` 都由代码去原文里找（`Source.locate`）：

1. 原文和摘抄都去掉空白和标点，摘抄短于 4 个字的直接不算；
2. 摘抄是原文的子串 → 通过；
3. 否则把摘抄切成字符三元组，≥60% 能在原文里找到 → 通过；
4. 不通过的事实直接丢弃并计数（`factsUnverified`）。

找到的位置还用来判断这条事实属于哪一章（合并块里有多章时）。

### 读两遍（`rounds: 2`，默认）

第一遍读完全书后，再从头读第二遍。第二遍的提示词里列出**本块原文里出现过名字 / 别名**的已知实体（由代码判断，最多 15 个，
每个附 4 条已知事实），只要模型补「这些实体的新事实」和「第一遍漏掉的实体」。所以必须等第一遍全部完成才开始第二遍；
同一遍内的块可以并发（大模型按配置的并发数，GGUF / 本地模型一次一块）。

### 聚合（代码，不用模型）

- 同分类 + 规范化名称（去空白和标点、小写）或任一别名相同 → 同一个实体；
- 事实按字符二元组重合去重（较短那条 ≥60% 出现在已有事实里就算重复），每个实体最多保留 80 条；
- 结果按事实数从多到少排序，存进提取结果的 `entities`（每条事实带章节标题和章节下标 `ci`）。

### 截断修复

输出被 `max_tokens` 截断时，退回到最后一个完整的 `}` 并补齐括号再解析（`_close_truncated`），前面写完的实体不丢。

## 3. 整理卡片（`compile_cards`）

输入只有实体档案和章节摘要（很短），所以可以换模型、换范围多次整理。

- **素材卡**：事实 ≥2 条的实体每个一次调用；只有 1 条事实的同分类 5 个一批。输出：
  `useful`、名称、细分类型、一句话概括、100–300 字详细描述、按分类模板填的属性、「作者用法」（原作怎么用它制造冲突）、
  「借用提示」（借到别的小说时哪些可直接用、哪些要改）、标签。
  - 提示词：只依据给出的事实，不编造、不补充原因或来历，没依据的属性直接省略。
  - `useful: false`（只有空泛情绪或一次性动作）不进候选箱，计入 `notUseful`。
  - 属性值是「无 / 未提及 / 无明确信息」这类空话的，代码直接丢掉（`_EMPTY_VALUE`）。
- **体系卡**：同一本书里同一细分类型的世界观卡 ≥3 张时，再合成一张「XX 体系」：组成、层级与顺序、核心规则、代价、限制。
- **剧情段**：章节摘要每 20 章一个窗口（相邻窗口重叠 3 章），找跨章的完整剧情段，抽象成骨架：起因 / 冲突 / 转折 / 结果 / 功能
  （开局、打脸、升级、反转、救场、揭秘…），人物用「主角 / 对手 / 甲 / 乙」代称，不留原作专有名词。
  同名或章节范围重叠 >50% 且功能相同的只留一个。

分类属性模板：

| 分类 | 属性 |
|---|---|
| 怪物 | 外形、能力、弱点及原因、习性、社会结构、来源、与人类的关系 |
| 世界观 | 规则内容、代价、限制、谁能打破、对社会的影响 |
| 物品功法 | 作用、代价、获取方式、限制 |
| 角色 | 人设核心、反差、能力、动机、关系、名场面 |
| 势力 | 结构、目标、资源、内部矛盾 |
| 地点 | 特征、危险、特殊规则、产出 |
| 情节 | 起因、冲突、转折、结果、功能 |

结果进入「待确认」候选（`material_candidate`）。同一本书已有的同分类同名候选或素材自动跳过。

## 4. 断点续跑与任务状态

长篇小说用 GGUF 要跑十几个小时，必须能断开后接着做。

### 断点

`data/extract-cache/<key>/`：

- `meta.json`：指纹。提取用 文件 / 字数 / 分块字数 / 块数 / 遍数 / 分类 / 特别关注；整理卡片用 实体键和事实数的哈希 / 是否整理剧情段 / 章节数。指纹变了（换了参数）就清空重来，避免把不同切法的结果拼在一起。
- `pass1.jsonl` / `pass2.jsonl` / `chunks.jsonl`（不记实体时的章节分析）/ `cards.jsonl` / `systems.jsonl` / `arcs.jsonl`：每读完一块、整理完一批卡就追加一行并 fsync；最后一行写到一半被打断时读取跳过。
- 断点键：提取 `e<任务 id>`，整理卡片 `k<任务 id>`。结果保存成功后删除断点。

### 状态

| 状态 | 什么时候 | 能做什么 |
|---|---|---|
| 排队中 / 运行中 | 刚提交 / 正在跑 | 暂停、取消 |
| **已中断** | 服务重启、AI 服务不可达、模型出错、用户暂停 | 继续（从断点接着做）、取消 |
| 成功 | 跑完并保存结果 | 查看（提取任务不能删） |
| 失败 | 只有用户点「取消」才会到这里 | 查看、删除（连同断点） |

「继续」时如果 Python 里同一个任务还在跑（只是 Java 重启了），直接接着轮询它，不重复提交；Python 也会拒绝在仍被占用的断点键上再起一个任务。

## 5. 实测（本地 GGUF）

机器：RTX 4060 Laptop 8GB；模型：Qwen3-4B-Instruct-2507 Q4_K_M（llama.cpp）；样本：《耐瑟瑞尔的辉煌》前 6 章，13,609 字。

| | 读 1 遍 | 读 2 遍 |
|---|---|---|
| 总耗时（含整理卡片） | 574 秒 | 971 秒 |
| 实体数 | 19 | 25 |
| 核实通过 / 丢弃的事实 | 46 / 0 | 119 / 13 |
| 实体召回（以 2 遍的名称和别名为基准） | 12 / 27 | 27 / 27 |

折算：每遍每千字约 **16 秒**，整理一张卡约 **18 秒**。313 万字的全本读一遍约 14 小时，所以分步、暂停和继续很重要。
整理卡片改用大模型能省掉卡片那部分时间。对照：旧版一次提取全本用 DeepSeek 花了约 12 元，而且约 40% 的输出花在被丢弃的候选上。

评测脚本：`python-service/scripts/extract_eval.py`（同一段样本比较不同模型 / 遍数的耗时、token、核实率、实体召回，并排展示卡片）。
