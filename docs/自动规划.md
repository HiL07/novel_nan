# 自动规划：一句构思 → 设定 + 10 章大纲 + 伏笔计划

> 相关代码：Python `app/generation/planner.py`（每一步 + 代码检查）、`facts.py`（计划中的伏笔 / 定时事件、`sync_outline`、`check_outline`）、
> `ideas.validate_outline`（大纲的规划字段）、`spec.py`（写作参数 → 【作品定位】）；Java `NovelPlanService` / `NovelPlanController`（`/api/novel/plan/{id}/*`），
> 检索复用 `InspirationService.retrieveNeeds`；前端 `components/novel/PlanWizard.vue`（工作区「自动规划」页）、`BookConfigForm.vue`（写作参数）、
> `BookSkeleton.vue`（全书骨架）、`novel-options/materialApply.js#applyPlanItem`（写进设定编辑器）。评测 `python-service/scripts/plan_eval.py`。

**两条路线**（页面顶部切换，记在 localStorage `nan_novel.plan.mode`；素材库是空的只能走故事优先）：

- **故事优先**（默认，§7）：写作参数 + 灵感 → 全书骨架 → 设定（从骨架推出）→ 素材点睛（可跳过）→ 当前阶段 10 章大纲 → 审稿 → 写进工作区。
  不需要素材库；素材只在「点睛」那一步给已有设定补细节。
- **素材优先**（§1–§6，原流程）：一句构思 → 拆需求 → 选素材 → 设定草案（素材改编）→ 10 章大纲 → 审稿 → 写进工作区。

## 1. 做什么、不做什么

输入一句构思（「法师喜欢冒险」），AI 按素材库选配并改编出**写小说要用的规划**：

- 设定：世界规则、主角（欲望 / 缺陷 / 秘密 / 带代价的能力）、配角（第几章登场）、势力 / 地点 / 物品 / 怪物（量级、登场章）、阶段表
- 10 章大纲：每章 目标 / 节拍 / 出场人物 / 新名词 / 伏笔动作 / 定时事件 / 章末钩子 / 开篇要点
- 伏笔计划与定时事件：写进故事账本，状态「计划中」

**不生成正文，不改写作流程**。写不写、什么时候写由作者在「写作」页决定；写到某章时，现有的摘要提取看到计划中的编号会把它转成「已埋下」。

## 2. 流程

```
① 拆需求（1 次调用）  复用灵感墙 inspire.plan：开篇 → 阶段 = 开篇、对手量级上限 2；需要 主角原型 / 世界规则 / 配角 / 对手 / 势力 / 地点 / 物品 / 传说
② 选素材（本地，不花 token）  InspirationService.retrieveNeeds：向量 + BM25 + 重排、StageFit、每书 ≤2；
                       relaxEmpty：一条需求没素材过相关度线（30）时给最接近的 2 条，标「相关度低」、默认不勾
③ 设定草案（1 次调用）  素材改编：保留骨架（能力 / 代价 / 冲突 / 关系），名字地名组织名换新，adapted 写改了什么，sources 记素材
                       代码查：素材原名出现在草案里（泄漏）、前 10 章登场的敌对元素超量级、主角缺欲望 / 缺陷 / 秘密
④ 大纲（1 次调用）      伏笔用 P1… / 定时事件用 K1…；计划章节以每章的引用为准（第一次 plant = 埋下章，resolve = 回收章）
                       代码查：章末钩子、开篇前 3 章新人物 ≤3 / 新名词 ≤5、人物早于登场章出场、伏笔没埋 / 隔得太近（<2 章）/ 10 章里一条都不收
⑤ 审稿（1 次调用）      逐章问题 + 修正版（冲突保留甚至加强），作者逐章「采用修正」/「恢复原版」；另附整体意见和代码检查
⑥ 写进工作区（不用模型）设定 → 设定编辑器（applyPlanItem 按字段写，appearFrom → 出场条件，量级 → 备注）并保存；
                       大纲 + 伏笔 / 定时事件 → Python plan/apply：账本建「计划中」条目，大纲里的 P / K 换成账本编号
```

默认逐步确认；「一键全自动」= 过线素材全用、审稿修正全部采用，停在「写进工作区」前。
每一步的结果存在 `data/novels/<id>/plan-draft.json`，刷新不丢；已写过章节的工作区规划「接下来 10 章」（局面来自世界书，
可以推进 / 回收账本里已有的伏笔，不套开篇规则）。新建工作区时填「一句构思」直接进入这一页。

## 3. 开篇规则（只作用于规划）

`planner.OPENING_RULES`，进 ③④⑤ 的提示词：第 1 章开场就有冲突或悬念、主角亮出欲望和缺陷、章末激励事件；前 3 章确立核心卖点；
世界观随情节露出（不安排「介绍世界」的章节）；每章新出场有名有姓人物 ≤3、新专有名词 ≤5（代码数大纲的 cast / newTerms）；
对手量级 ≤ 阶段上限；每章章末钩子。每章可带「开篇要点」给作者写作时参考。

## 4. 计划中的伏笔：账本、大纲、世界书是同一份

- 账本 `foreshadows[]` / `clocks[]` 加 `status: planned` + `planned: true` + `plannedIn`（计划埋 / 定下的章）+ `payoffIn` / `dueIn`。
  没有历史记录也不会被删章回滚清掉；写到那章时摘要提取引用编号 `plant` → `open`；删掉那章 / 重新提取 → 回到 `planned`。
- 大纲每章 `foreshadow[{id, action}]` 只引用账本编号；AI 构思页的大纲有「故事账本」开关：每章显示埋 / 推 / 收哪些伏笔（悬停看全文和状态）、
  定时事件、节拍、钩子；编辑时可增删引用，「采用大纲」时 `facts.sync_outline` 按引用改账本里计划中伏笔的计划章节。
- 世界书：`threads` 带计划字段，局面快照有【计划中的伏笔】（标「本章该埋 / 已超期」）和【计划该回收的伏笔】，走向引擎能看到；
  `checks` = `facts.check_outline`：大纲引用了不存在的编号、两边计划章节不一致、计划章节已过还没埋 / 没收。

## 5. 实测（端到端，DeepSeek，「法师喜欢冒险」，素材库 15052 条）

拆需求 3 s / 1k token → 检索 47 s（首次加载向量与重排模型）→ 设定 17 s / 5k → 大纲 25 s / 7.5k → 审稿 28 s / 8.5k，合计约 2.3 万 token。
8 条需求里 2 条没有素材过相关度线（魔法代价、法杖物品）——这就是加 `relaxEmpty` 的原因。
素材确实被改编（「收破烂式冒险者」+「消化菌天赋」→ 主角；「骷已己」→ 骷髅向导），泄漏检查报出了照搬的「消化菌天赋」，
也误报了「法师公会」这类通用词（作者可以保留）；审稿对 10 章都给了修正版，所以修正必须逐章由作者决定。

## 6. 评测（`plan_eval.py`，2026-10-30）

4 个构思（法师喜欢冒险 / 废柴少年靠收破烂逆袭 / 被退婚的大小姐开了家侦探社 / 末世里开奶茶店的普通人），每个建两个空工作区：
自动规划（一键全自动：过线素材全用、修正全采用）对比原来 AI 构思的「生成大纲」（同一批素材、构思方向 = 这句构思、10 章）。
DeepSeek 裁判给每份规划打 1–5 分，再整份两两比较（位置随机）。

| | 自洽 | 精彩 | 开篇 | 人物 | 伏笔 | 可用 | 耗时 | token |
|---|---|---|---|---|---|---|---|---|
| 生成大纲（旧） | 3.00 | 3.00 | 2.75 | 3.00 | 3.25 | 3.25 | 10 s | 2.8k |
| 自动规划 v1 | 3.25 | 3.00 | 3.25 | 3.25 | 3.50 | 3.75 | 87 s | 14.5k |
| **自动规划 v2（采用）** | 3.50 | 3.25 | 3.50 | 3.75 | 4.00 | 4.00 | 69 s | 19.5k |

两两比较（自动规划胜 / 旧胜，共 4）：v1 自洽 4/0、开篇 4/0、总体 4/0、**精彩 1/3**；v2 自洽 4/0、开篇 4/0、总体 4/0、精彩 3/1。

- **v1 → v2**：v1 的审稿 4 次里 3 次被截断（`max_tokens` 5000 装不下 10 章逐章问题 + 修正版），等于没审；
  改成 8000、每章问题 ≤3 条、只给问题严重的章写修正版（≤5 章）、修正版不许人物提前登场。大纲提示词加上走向引擎验证过的
  「不要保守：每章强冲突 / 强悬念，主角主动出手，合理不等于平淡」——v1 和走向引擎 v1 一样，精彩度输给了更「敢写」的旧流程。
- JSON 坏了（长输出里没转义的引号）会降温重试一次（`planner._call`）；审稿两次都失败时只返回代码检查，流程不卡住。
- 裁判评语里旧流程的通病是「元素堆叠、主线被稀释、开篇平淡、主角被动」，自动规划是「设定闭环、伏笔埋收清晰，但爽点密度还可以更高」。
- 局限：样本只有 4 个构思，裁判和被测都是 DeepSeek；泄漏检查仍会报通用词（「法师公会」），由作者判断。

## 7. 故事优先：不用素材库也能成书

### 7.1 为什么加这条路线

素材优先的流程从头到尾围着素材转：第①步拆的是「要从素材库选什么」，第③步是「把素材改编成设定」，SYSTEM 也写着「擅长从素材出发」。
素材库里没有合适的东西时，提示词里只剩一句「没有选素材，自己构思」，设定和大纲都显得单薄；而且只规划 10 章，写完就没了方向。

对照 easy-writing（易创）的「工作流建书」（灵感 → 大纲 → 设定 → 逐章写，不用任何素材也能出像样的规划），它靠的不是 skill，而是三点：

1. **入口信息足**：一句话先扩成「核心设定 + 主角处境 + 核心冲突 + 爽点方向」，写作参数（平台、题材、读者、卖点、人称、字数）每一步都带上；
2. **先有全书骨架**：大纲先定分卷 × 阶段（目标、起止状态、必须发生、禁止发生），章纲按阶段一批批补；
3. **设定的 JSON 结构本身就是「要填满的清单」**：世界背景卡 4–6 张、力量体系 4–8 个境界、能力 / 机制 / 资源各若干——
   模型只能用题材常识把每个槽位填满，「法师 + 西幻」自然就填出浮空法师塔、学徒 → 法神的境界链、魔力潮汐这类东西。

### 7.2 流程

```
① 写作参数 + 灵感（1 次调用）  idea：一句话（可空）+ 创作方向 + 写作参数 → 3 个明显不同的灵感
                              {title, core 核心设定, situation 主角处境, conflict 核心冲突, payoff 爽点方向, hook 一句话卖点}，作者选一个再改
② 全书骨架（1 次调用）          book：titleOptions / logline / storyHook / sellingPoints / worldPoints + 2~4 卷，
                              每卷 1~3 个阶段 {title, chapters, goal, startState, endState, power, mustHappen[], forbidden[], tierMax}；
                              各卷章数 ≈ 目标字数 ÷ 单章字数（没填 = 300 章）；第一阶段 tierMax 代码压到 ≤2
③ 设定（1 次调用）              settings(mode=story)：从骨架推出，提示词里没有素材块（选了素材才作为「可选参考」）。
                              槽位：world.rules / note / cards[4~6] / power{intro, realms[4~8]{name, desc, cost}, beyond} /
                              abilities{innate, acquired, dimensions} / mechanics[2~5] / resources[2~5] + 人物 4~7 + 元素 4~8；
                              阶段表由代码按骨架算（book_stages），不让模型另写一份
④ 素材点睛（可选，1 次调用）    enrich：设定里每个人物 / 元素当一条检索需求（Java 本地检索，只要过相关度线 30 的，每个 ≤2 条，≤12 个对象）
                              → 模型逐条给「补细节」建议（能力代价、弱点、内部矛盾、秘密…，只能写进这个对象已有的字段，不改名、不推翻）；
                              作者逐条「采用 / 撤销」。一条都没检索到就不调模型
⑤ 10 章大纲 ⑥ 审稿 ⑦ 写进工作区：同素材优先，另外带【全书骨架】和【当前阶段】
```

「一键全自动」= ①（取第一个灵感）→ ② → ③ → ⑤ → ⑥（修正全采用），不做点睛，停在写进工作区前。

### 7.3 全书骨架怎么用

- **章节落在哪个阶段**：`book_layout` 按卷 / 阶段章数排出每个阶段的章节范围（阶段没写章数就平分本卷剩下的，卷没写按 30 章），
  `book_position(book, n)` 查第 n 章所在阶段。前端 `api/novelPlan.js#bookLayout` 是同一规则。
- **大纲 / 审稿**：`stage_block` 写【当前阶段】（目标、起点 → 终点、必须发生、不能发生）。阶段在这 10 章内结束 → 要求到那章达到终点状态，
  并预告下一阶段；没结束 → 「推进目标，不要提前达到终点、不要提前解决本阶段的核心冲突」（对应 easy-writing 的 `planFinal`）。
  审稿多查「偏离阶段目标、写了不能发生的事」；代码检查 `stage_issues`：阶段在这批章节里结束时，「必须发生」逐条和章节目标 / 节拍比字二元组重合度，< 30% 提示。
- **阶段表**：骨架的每个阶段 → 设定编辑器阶段表的一行（范围、主角实力 = power 或终点状态、对手上限、备注 = 阶段目标 + 必须发生），
  所以写正文时【当前阶段】、灵感墙 / AI 构思的量级过滤都不用改代码就跟着骨架走。
- **存储**：写进工作区时（勾「全书骨架和写作参数」）存 `novel.book` / `novel.bookConfig`，不放进 `novel.outline`（AI 构思页「采用大纲」会整份替换大纲）。
- **滚动续规划**：写作页的大纲用完、工作区有骨架时出现「按全书骨架规划接下来 10 章」→ 自动规划页 `autoContinue`：骨架写完了先延长 1~2 卷
  （`book` 带上已有骨架 = 原样保留，只追加）→ 设定（续写模式，只补新东西）→ 大纲 → 审稿（修正全采用）→ 直接写进工作区。

### 7.4 写作参数 → 写正文

`novel.bookConfig {platform, genre, tags[], audience, sellingPoint, pov, style, targetWords, chapterWords}`（`spec.clean_book_config`）：
`spec.build_for` 把除字数外的几项作为【作品定位】放在核心设定最前面（写章、规划节拍、一致性检查、AI 构思、走向引擎都能看到）；
`chapterWords` 是写作页目标字数的默认值（设定里明确设过「每章字数」的优先）。设定页顶部「作品定位」一行可以改（`POST /api/gen/novels/{id}/update {bookConfig}`）。

### 7.5 代码检查

- `book_issues`：相邻阶段终点 / 起点状态没写、阶段没有「必须发生」、骨架总章数和写作参数估算差 50% 以上；
- `story_issues`：开篇时槽位数量（背景卡 / 境界 / 人物 / 元素各 ≥ 4，否则「设定偏薄」）；骨架「必须发生」里用「」《》点名的东西设定里没有；
- 其余沿用 `settings_issues`（主角缺欲望 / 缺陷 / 秘密、量级超阶段、素材原名泄漏）和 `outline_issues`；
- 点睛建议里出现素材原名 → `leaks`（会把「黑市」这类通用词也报出来，作者判断）。

### 7.6 实测

端到端（DeepSeek，测试端口 + 数据副本，2026-10-30）：「法师，西幻冒险」+ 起点 / 西幻 / 冒险·升级流 / 100 万字，**零素材**：
灵感 5 s → 骨架 13 s → 设定 18 s → 大纲 24 s → 审稿 12 s，约 2.5 万 token。
得到 3 卷 333 章（火球矩阵 / 节点战争 / 禁咒法神，9 个阶段，对手上限 2 → 5）、背景卡（浮空法师塔、地下矩阵黑市、古代矩阵遗迹、节点密码学、魔物苏醒传说）、
境界（学徒 → 初级 → 中级 → 高级法师 → 矩阵大师 → 法神）、机制 4 条、资源 3 种、6 个人物、8 个元素；代码检查报出「法师协会量级 3 却第 1 章登场」和 5 处人物早于登场章出场。
点睛（检索 14 个对象，命中 20 条素材，37 s / 5.8k token）给出 8 条：主角自创连线的精神反噬代价、协会保守派 / 改革派的内部矛盾、导师因古代矩阵反噬失明……
续规划：第 11 章起正确落在「火球开花」阶段（1–40 章）；延长骨架追加第 4 卷，前 3 卷原样保留。

**评测**（`plan_eval.py --compare story`，2026-10-30，6 个构思：原来 4 个 + 「古董修复师能看见器物的记忆」「深海潜艇里的末日教团」；
写作参数只给字数；裁判 DeepSeek，1–5 分 + 两两比较，位置随机）：

| | 自洽 | 精彩 | 开篇 | 人物 | 伏笔 | 可用 | 耗时 | token |
|---|---|---|---|---|---|---|---|---|
| 故事优先·零素材 | 3.83 | 3.83 | 3.83 | 3.50 | 3.83 | 4.00 | 76 s | 2.6 万 |
| 故事优先 + 点睛（全采用） | 3.67 | 3.83 | 3.67 | 3.67 | 3.67 | 4.00 | 132 s | 3.4 万 |
