## 1. 要解决的问题

素材提取出来了，但不知道怎么用。作者想要的流程：

```
描述一个大概方向 → 自动检索对应的素材 → 我从结果里选 → 结合选中的素材生成
```

两个核心步骤是「语义分析和检索」「素材融入和 AI 生成」，另外缺一个评判标准：怎么知道素材真的有用。

**范围**：自动规划的「参数 · 灵感」和它后面的「设定」这两步。不是书房里的设定页。写章节怎么用素材、原素材改写到什么程度，先放着。

## 2. 现状

### 2.1 参数 · 灵感：检索（读过代码）

点「按参数推荐」之后：

1. `PlanWizard.vue#openMatPicker` 把写作参数（每项写成「名称：值」）、创作方向、你的想法、补充要求用「；」拼成一条查询，截到 500 字。平台、读者、人称、字数这些和素材无关的参数也在里面。**没有语义分析**。
2. `MaterialService.vectorSearch(..., kind = "portable")`：候选池只有架空版，不限分类，最多 2 万条（超出按使用次数、更新时间截）。
3. 每条素材的检索文本（`vectorText`）= 名称 + 细分类型 + 标签 + 概括 + 所有属性的值。架空版的属性由 `applyPortable` 从档案拼出：可移植度、叙事用途、换世界时替换（原作词 → 新词）、一定保留、原作绑定、节点对应、通用联动。
4. Python `embedding.search`：向量（bge-small-zh-v1.5）取前 50、BM25（jieba）取前 50 → RRF（k = 60）取前 30 → bge-reranker-v2-m3 重排，分数 0–100。
5. `MaterialPicker.vue#onOpen`：重排过的只预勾 30 分以上、非远景的，最多 5 条。
6. 作者确认后进素材篮，最多 8 条（`MAX_PLAN_MATERIALS`）。

### 2.2 参数 · 灵感：融入（读过代码）

- `NovelPlanService.idea` / `assist` 调 `portableMaterials`，**没有架空档案的素材直接丢掉**，不报错。
- `planner._portable_block` 把每条素材写成一行，只用档案字段：
  `[S1]【分类】通用名：内核（≤160 字）。叙事用途：…。一定保留：…。换世界时可以换成：…。节点角色：…。联动规则：…`
  不写来源书、原作绑定、示例正文。
- `planner.idea` 的提示词顺序：作者的想法 → 创作方向 →【写作参数】→ 补充要求 →【之前几批的反馈】→【主次】+【可参考的架空素材】→【任务】。
- 【主次】原文：「上面作者写的内容是主体，必须保留、不能被替换；下面的架空素材只是补充，用来让内容更具体、更有新意。可以借用素材的机制、用途和关系，但名字要起新的，输出里不要提到素材的名称；不要把素材原样搬进来，也不要让素材盖过作者的想法。」
- 带素材时任务里多两句：「每个灵感至少用上一条架空素材的机制或用途（起新名字），但故事的核心必须来自作者的想法和创作方向。」「另外输出 sources（用到的素材编号）和 used（用了素材的哪一点，20 字内）。」
- 一次调用，温度 0.95，输出上限 2500 token（带素材 6000）。
- 代码核对编号，对不上的去掉；一条都没对上的灵感标「没用上素材」。
- 素材篮还用在 4 个小帮手里（核心卖点、文风、你的想法、补充要求），每处有开关；文风只用写法类。

**现在的三个缺口**

| 缺口 | 具体情况 |
|---|---|
| 检索没有语义分析 | 查询是参数原样拼接，一条查询一个向量 |
| 看不出每条素材借了什么 | `used` 是整个灵感共用的一句话，被贴给这个灵感引用的所有素材（`planner.py` 里构造 `x["materials"]` 的那几行），页面只显示第一条的 |
| 「没用上素材」不可信 | 提示词强制每个灵感至少用一条，模型是被要求引用的 |

### 2.3 设定这一步（读过代码）

`planner._settings_story` 已经能接收素材：用 `inspire._material_block` 编号，提示词里有「【可参考的素材】（可选：用得上就改编进来，名字换新，sources 写编号；用不上就不用）」，生成后 `settings_issues` 查素材原名泄漏。**但前端 `PlanWizard` 发请求时不带素材 id，所以这一段从不出现。** 参数 · 灵感的素材篮到这一步就断了，只有选定灵感的 6 栏文字往后传。

### 2.4 其他位置（前端和生成侧各查了一遍，没有逐行读）

- 全书骨架、配角和元素：不用素材。「素材点睛」代码还在，入口已拿掉。
- 书房设定页：素材复制成设定文字（`materialApply.js`），或在 AI 填写前选作参考，结果不标来源。写法、共鸣两类没有 `APPLY_TARGETS`，加入设定会报「不支持的素材分类」。
- AI 构思：手选作参考，大纲里只留素材标题。
- 写章节：不读素材库，素材只能经设定间接生效。
- 「方向 → 拆需求 → 检索 → 勾选 → 带引用生成」这一整套只有灵感墙用全了（`inspire.plan`、`InspirationService.retrieveNeeds`）。

## 3. 两个怀疑

### 3.1 检索：一句话有很多角度

作者的怀疑：同一句话可以从不同角度理解，维度太多。

判断（推断，没有实测）：

- **一句话只有一个落点。**「破产法师继承法师塔，靠经营翻身」里有主角处境、场所、玩法、冲突、力量体系几个角度，各自要找的素材分类不同。一个向量落在它们中间，结果会被字面最强的词带走。评测里只用向量首条命中 59%，只用 BM25 有 76%，字面匹配占主导。
- **相似不等于有用。** 相似度检索找到的是和已写内容像的东西；构思阶段有价值的往往是这句话里没有的东西。2026-11-08 实测里起作用的三条素材（血脉骑士制度、重甲侍从、爽点节奏）和那句想法没有一个词相同，它们是手挑的，不是检索出来的。
- [素材检索](素材检索.md) §8 的 84% 首条命中，测的是「描述一条素材能不能把它找出来」，不是「给一个故事方向能不能找到有用的素材」。后者没有数据。

学术上这两个问题叫多角度检索和推理型检索，见第 4 节。

### 3.2 融入：素材是专精的

作者的怀疑：素材应该专精于某一个的生成，不具备通用性。

判断（从提示词和数据结构推出，没有实测）：

- 参数 · 灵感的一个灵感只有 5 栏，每栏不超过 80 字，一条素材最多占半句话；【主次】还在主动稀释它。
- 同一篮素材原样喂给 5 个用处，只有文风会筛出写法类。
- 素材的内容在后面的步骤里各有对口的位置：

| 素材类型 | 它有什么 | 对口的生成 |
|---|---|---|
| 世界观、体系、共鸣 | 规则、代价、限制、层级、联动 | 设定的世界规则、力量体系、世界机制 |
| 物品功法 | 作用、代价、获取方式 | 设定的能力、关键资源 |
| 角色 | 人设核心、反差、动机 | 主角卡、骨架那一步的配角 |
| 势力、地点、怪物 | 结构、目标、危险 | 骨架那一步的元素 |
| 剧情段 | 起因、冲突、转折、结果 | 全书骨架的阶段 |
| 写法 | 节奏、钩子、爽点套路 | 大纲、写章节 |

结论：不做「一个素材篮到处用」，改成每个生成的槽位只拉自己对口的那一类。参数 · 灵感这一步更适合手挑一两条想用的机制当起点，不适合自动检索。

## 4. 调研到的技术

每个方向只搜了一两轮，数字来自摘要和二手综述，没有读论文全文。推特上的原帖没有直接搜到。专门针对「小说素材库」的研究没有找到，下面都是相邻领域。

### 4.1 检索

| 技术 | 做法 | 证据 | 判断 |
|---|---|---|---|
| 用途 / 机制分开表示 | 每条东西拆成「用来干什么」和「怎么做到的」两个向量，找用途相近、机制不同的 | 用户实验里这样找出的远类比让人产生更多点子。[Analogy Mining](https://ar5iv.labs.arxiv.org/html/1706.05585)、[Analogical Search Engine](https://arxiv.org/pdf/2205.15476) | 适合：素材已有作者用法、叙事用途、内核这些字段 |
| 入库时生成假设性问题（HyPE） | 入库时让模型给每条写几个「什么情况下会需要它」的问题，检索时匹配这些问题 | 召回 71.5，普通做法 53.6；查询和文档文风差别越大提升越大。[论文](https://arxiv.org/pdf/2607.29402) | 适合：方向是故事口吻，素材是设定口吻 |
| 带推理的查询改写 | 先让模型想清楚需要什么样的东西再搜 | [BRIGHT](https://fugumt.com/fugumt/paper_check/2407.12883v4_enmode) 上最多提升 12.2 分；[ReasonIR](https://ai.meta.com/research/publications/reasonir-training-retrievers-for-reasoning-tasks/) 从 24.4 升到 29.9 | 适合，按槽位改写 |
| 多查询融合（RAG-Fusion） | 一句话换几种说法各搜一遍再合并 | [戴尔 2026 年的线上研究](https://arxiv.org/pdf/2603.02153v1)：已有重排时没有提升，命中率从 0.51 降到 0.48 | 不推荐 |
| 大模型做列表重排 | 前几十条一起交给大模型按任务挑 | [一个评测](https://www.zeroentropy.dev/articles/llm-as-reranker-guide/)：0.78 对 0.74，成本 9 倍、慢 35 倍 | 只放在最后一小步 |
| Multi-Head RAG | 用注意力头的激活值当多个角度的向量 | [论文](https://arxiv.org/abs/2406.05085v4)称检索成功率最多提升 20% | 不推荐：工程量大 |
| 关键词触发 | 正文里出现某个词就注入对应条目 | [SillyTavern World Info](https://docs.sillytavern.app/usage/worldinfo) 的默认做法 | 适合写章节，不适合构思 |
| 换向量模型 | Qwen3-Embedding、bge-m3 | 没找到中文上明确优于现有模型的可靠对比。[Qwen3 Embedding](https://arxiv.org/pdf/2506.05176) | 不建议现在做：答案进前 30 已是 97% |

### 4.2 树状检索

| 工作 | 结论 |
|---|---|
| [RAPTOR](https://www.themoonlight.io/review/raptor-recursive-abstractive-processing-for-tree-organized-retrieval) | 作者自己比较：把树上所有节点摊平一起搜，比逐层往下走好 |
| [TreeHop](https://arxiv.org/pdf/2504.20114) | 重测：逐层走在每个数据集上都更差，上层被剪掉后下面的内容够不着 |
| [LATTICE](https://arxiv.org/html/2510.13217v1)（[代码](https://github.com/nilesh2797/lattice)） | 让大模型读节点摘要决定往哪走，允许回头。BRIGHT 上召回最多 +9%、排序 +5% |
| [PageIndex](https://yuv.ai/blog/pageindex) | 不用向量，建目录树让大模型翻。自称的 98.7% [需要自己验证](https://rubinlake.com/en/technology-radar/ai-and-data-engineering/pageindex)，比向量查找慢、贵 |

结论：树可以用来检索，但往下走的每一步要么是人选，要么是大模型判断，不能交给向量。

### 4.3 人定主干、AI 补全

| 工作 | 做法 | 可借用的 |
|---|---|---|
| [HiExpan](https://astro.paperswithcode.com/paper/hiexpan-task-guided-taxonomy-construction-by)、[CoRel](https://arxiv.org/abs/2010.06714) | 用户给种子树，系统沿宽度和深度补全 | 思路成立（大模型之前的方法） |
| [TopicGPT](https://arxiv.org/abs/2311.01449v2) | 人给种子主题，大模型补充和精简，再把文档归到主题下并给出一句支持的原文 | 归类时摘一句原文作依据。吻合度 0.74，最强基线 0.64 |
| [LLooM](https://arxiv.org/pdf/2404.12259) | 每个概念带明确的收录标准，大模型按标准打 0–1 分；人可以给种子 | 主干要写成可判断的标准，不能只有名字 |

## 5. 已经定的

1. 参数 · 灵感放开原素材（现在只收架空版），卡片上标明原素材 / 架空版。
2. 评判方式第一版：每条结果标出借了哪条素材的哪一点；选了但没用上的单独列出；一键生成带素材和不带素材两版并排比较。
3. 设定的素材在进入设定时重新检索，和参数 · 灵感的素材篮分开。
4. 先做检索测试，再定产品方案。测试放在本项目的 `python-service/lab/retrieval/`，数据不进 Git。
5. 现有素材不删。新做法都是在现有素材之上加东西（拆字段、补字段、建树），不需要重新提取。
6. 素材树：
   - 作者定主干，例如「力量体系」「剧情走向」「写作手法」「角色内核」。
   - AI 在主干下延伸出枝，例如「魔法力量体系」「骑士力量体系」「冷静系角色内核」「陈述手法」。按类型分，不按用途分。
   - AI 负责把素材归到主干和枝上，作者可以手动添加和调整。
   - 一条素材可以挂在多处；作者手动动过的不被 AI 覆盖；AI 只能加，作者定的主干和枝它不改不删。

## 6. 候选方案（都没有验证过）

### 6.1 多个检索方向

把每条素材拆成几个方向分别建索引，查询只匹配其中一个：

| 方向 | 用哪些字段 | 回答什么 |
|---|---|---|
| 是什么 | 名称、细分类型、概括 | 找一个这样的东西 |
| 怎么运转 | 内核、规则内容、层级、联动规则 | 找一套这样运作的机制 |
| 代价和限制 | 代价、限制、弱点、谁能打破 | 找有这种代价的设定 |
| 能起什么作用 | 作者用法、叙事用途 | 找能制造这种冲突的东西 |

- 量级、分类、原素材 / 架空版只做过滤，不进向量。
- 由正在生成的槽位决定搜哪个方向（路由），不要每次全搜再合并，否则等于又混回一个向量。例如力量体系 → 怎么运转 + 代价和限制；核心冲突 → 能起什么作用；主角 → 是什么 + 能起什么作用。

### 6.2 入库时生成「什么时候会用到它」的问题

例：血脉骑士制度 →「需要一个让力量被少数人垄断的制度」「主角出身低微，怎么设置上升的门槛」。约 1.5 万条素材各调用一次，一次性成本。

### 6.3 检索分两段

先选主干（作者点，或大模型从十几个主干里挑，一次调用），主干内部摊平了搜。这样用上了树，又避开「逐层往下走不如摊平」的问题。

### 6.4 素材树怎么建

1. 作者写主干，每个带一句收录标准。
2. AI 归类：每次判断给出素材里的一句原文作依据。挂不上的放一堆，AI 从这一堆里提议新主干。
3. AI 在主干下补枝：先往已有的枝上挂，剩下的分批让大模型找共同点，每种给名字和收录标准；意思相近的合并；和已有的枝太近的改成建议并入。
4. 规矩：新枝至少 3 条素材才成立；提议存下来不每次重算；层数封顶（主干 → 枝 → 素材，最多再加一层）；AI 可以提议改主干，由作者决定。

两点观察：

- 作者举的主干和现有分类基本对得上（力量体系 ≈ 世界观 / 体系类，角色内核 ≈ 角色，写作手法 ≈ 写法，剧情走向 ≈ 情节），也和 [素材提取改造方案](素材提取改造方案.md) 的设定 / 剧情 / 写法三层对得上。第一层归类大部分可以按现有分类走，不用调模型。
- 素材已有「细分类型」字段。新枝也许可以从它起步：收集同一主干下所有的细分类型，让 AI 合并成几个枝。这个字段实际填得怎么样还没看过，要先统计。

成本：1.5 万条乘以十几个主干逐个判断太贵。可以一条素材一次调用、把全部主干列给模型多选；或者先标一部分再训练小分类器。

### 6.5 拓展枝干的 skill（在应用里，对话式）

2026-11-12 作者更正：这个 skill 不是给 Claude Code 用的，而是**应用里的一个对话窗口**，由模型配置里选的对话模型来跑——DeepSeek、其他兼容接口的模型，或通过 API 接入的 Claude。`llm_client` 已支持 OpenAI 兼容和 Anthropic 两种接口（读过代码），但没有各家自带的「工具调用」。下面是草案，图见 <https://claude.ai/artifact/QXCNupWPCag5YWgtRyoPNx>。

**怎么跑**

- skill 是一份写给模型的说明：名称、什么时候用、步骤、规矩、能用的动作、回复格式。模型不认识「skill」，只是每一轮都读到它。
- 每一轮应用发给模型：skill 全文 + 树的当前状态（主干和枝的名称、收录标准、条数，不放素材正文）+ 最近几轮对话 + 作者这句话。
- 模型回 JSON：`{"say": "对作者说的话", "actions": [...]}`。用 JSON 而不用原生工具调用，是因为现有的 `llm_client.chat` 就这样用，两种接口都能直接跑。
- 动作分两类：
  - 只读（看树、抽样素材、统计、搜索素材）：应用直接执行，把结果接回去让模型继续。
  - 会改树（提议新枝、改名 / 改收录标准、合并枝、挂 / 移走素材、写共性摘要）：不执行，显示成待确认的卡片，作者点了才生效。
- 本地小模型能不能稳定输出这种 JSON 没测过，建议用大模型。

**一个枝干里存什么**：名称、挂在哪个主干、收录标准（一句话，归类靠它）、共性摘要（80–150 字，融入生成时用）、常见变体（2–5 条）、代表素材（3–5 条）、谁建的、成员（每条素材：谁挂的、依据的一句原文）。存在哪待定；做成应用功能的话按规矩应是 Java 管的两张表。

**枝干怎么创立**（数字是草案）

1. 作者写主干：名称 + 一句收录标准。
2. 素材归主干：现有分类能直接对应的不调模型；对应不上的一条一次调用、全部主干多选、摘一句原文，代码核对原文在素材里。
3. 发起分枝：作者直接建 / 对话里让 AI 提议 / 未归枝的攒够（如 30 条）应用提醒。
4. 先用向量分堆（代码，不调对话模型）：未归枝素材每条压成一行（编号｜名称｜细分类型｜概括 ≤60 字，素材已有概括，不用再压缩），用向量聚类，每堆 20–30 条。不直接把几百条交给模型分组：上下文太长容易漏、容易编（见下「控制上下文」）。
5. 模型每堆一次调用：能归进已有枝的写 `assign`；剩下的「是不是同一种？是就起类型名、写收录标准；明显混着两三种就拆开；一种至少 3 条；哪种都不像写 `none`」；编号只能用列出的。作者已定的枝原样列在提示词里，同时示范想要的粗细。
6. 合并各堆的结果：把所有候选枝的「名称 + 收录标准」列成一张短表让模型合并重复的，这一步不带素材正文；和已有枝太近的改成「建议并入」；不到 3 条的丢掉；编号不在这堆里的去掉。
7. 写共性摘要：给模型看成员的概括和属性，写「通常怎么运转」+ 常见变体 + 代表素材，不出现原作名字。代码核对：每一句要在至少两条成员里有字面重合（沿用 [精炼合并](精炼合并.md) 的规则）。然后打上「被找到」用的标记（见下「节点的标记」）。
8. 作者逐个决定：采用 / 改了再采用 / 并入别的枝 / 不要。作者改过的不被覆盖。
9. 正式挂素材：对主干下每条未归枝素材，先用枝的「收录标准 + 共性摘要」预筛出最接近的 3 个枝，再让模型一次只判断一个枝、摘一句原文，代码核对。可多挂；作者手动挂 / 移的不碰。

之后新素材入库：归主干 → 对该主干下的枝走第 9 步；成员变化大时提示重写共性摘要，不自动改。新素材只做「修改和补充」，不把整棵树重算。

**控制上下文**（2026-11-12 调研）

作者的担心：建新枝时直接调 API，上下文太长会出幻觉。调研结论一致——先压缩、先用向量分堆，模型每次只看一小堆，归纳和归类分开：

| 工作 | 做法 |
|---|---|
| [Context Rot（Chroma）](https://research.trychroma.com/context-rot) | 测了 18 个模型：输入越长越不可靠，无关内容越多越差 |
| [TnT-LLM](https://langchain-ai.github.io/langgraph/tutorials/tnt-llm/tnt-llm) | 每条先压成摘要 → 分小批 → 第一批生成初版，之后每批只做修改和补充 → 复查 |
| [LLooM](https://stanfordhci.github.io/lloom/api/operators.html) | 提炼要点 → 向量聚类 → 模型每次只看一个簇归纳概念 → 复查 → 打分 → 循环 |
| [Clio](https://arxiv.org/html/2412.13678v1) | 摘要 → 向量 + k-means → 模型给簇起名 → 对簇再聚类递归建多层；太小的簇丢掉 |
| [TopicGPT](https://github.com/chtmp223/topicGPT) | 只抽样一部分生成主题，每次带上已有清单；归类另做，一篇一篇判断 |
| [k-LLMmeans](https://arxiv.org/html/2502.09667v2) | 模型写的摘要当簇中心，调用次数不随数据量增长 |
| [LLM×MapReduce](https://arxiv.org/abs/2410.09342) | 切块处理再汇总，每块输出带依据和把握程度 |

对话里模型始终不持有素材：只看到树的概况，要看素材时通过「抽样」「搜索」取一小批；对话变长后早先几轮压成摘要。每堆 20–30 条是估的，没试过。这些工作处理的是对话、评论、论文，不是小说素材。

**节点的标记和枝干匹配**（2026-11-12）

作者的要求：树里要能精确匹配或大致匹配，选错枝会导致后面全错。做法：把每个主干和枝当成可检索的条目，检索文本是它的标记，用项目现成的检索（`embedding.search` 接受任意「编号 + 文本」，不限于素材）。

| 标记 | 谁填 | 用于 |
|---|---|---|
| 名称、别名 | AI 提议，作者改 | 精确匹配 |
| 特征词 | 代码从成员素材的标签统计：这一枝常见、兄弟枝少见的词 | 精确匹配 |
| 收录标准、共性摘要 | 已有 | 大致匹配 |
| 「什么时候会找它」的问题 | 模型写，每个节点一次调用 | 大致匹配 |
| 不收什么 | AI 提议，作者改 | 区分相近的兄弟枝 |
| 中心向量 | 代码算（成员素材向量的平均） | 大致匹配 |

- 精确：作者的话里出现枝名、别名或特征词，直接命中。
- 大致：向量 + 关键词两路在标记里找，重排打分。每个候选枝带分数和「凭哪个标记命中」。
- 四道保险：不只选一个（接近的都选，最多三个）；都不像就不选，退回整个主干搜；不管选了哪个枝都在主干里再搜一小批兜底，标「来自其他枝」；界面显示命中依据，作者能一键换。
- 几个枝分数很接近时才让对话模型判断一次。
- 作者改选后，把「当时那句话 → 最后选的枝」记成该枝一条新的「什么时候会找它」。
- 阈值待定，要拿真实的枝和查询试。

这替换了下面「生成时怎么调用」第 2 步里「让模型挑枝」的做法：检索为主，模型只在分不出来时判断。

**向量模型**（2026-11-12）

现在用的 bge-small-zh 较小。检索素材时有重排模型兜底，够用；但聚类分堆完全靠向量质量、枝干匹配时作者的话和标记文风差别大，这两处值得用更大的模型。这修正了 §4.1「不建议换向量模型」的说法——那一条只针对检索素材。

| 选项 | 情况 |
|---|---|
| [阿里云百炼 text-embedding-v4](https://help.aliyun.com/zh/model-studio/embedding-interfaces-compatible-with-openai) | 维度 64–2048，单条最长 8192 token，一次最多 10 条；文档写每千 token 0.0005 元 |
| [硅基流动 Qwen3-Embedding 8B / 4B / 0.6B、bge-m3](https://docs.siliconflow.cn/cn/api-reference/embeddings/create-embeddings.md) | Qwen3 系列单条最长 32768 token；国际站标 8B 每百万 token 0.04 美元，国内站价格没查到 |
| 本地的 bge-m3、Qwen3-Embedding-0.6B | 不花钱不联网；在 8G 显存上能不能跑没验证 |

- 两家接口都兼容 OpenAI 格式；重排也有 API（百炼 [qwen3-rerank](https://help.aliyun.com/zh/model-studio/text-rerank-api)、硅基流动 bge-reranker-v2-m3）。DeepSeek 据我所知没有向量接口（未证实）。
- 成本：1.5 万条 × 约 300 token ≈ 450 万 token，全部编码一遍约两三元。价格以各家控制台为准。
- 要改的：`app/local/embedding.py` 现在只支持本地模型，要加 API 后端；换模型后全部重新编码一次（缓存按模型分开）；API 不通时退回本地。素材内容会发给第三方，和现在发给 DeepSeek 做提取性质相同。
- 选哪个待定：在测试项目里用同一个主干的素材各聚一次，作者看哪边的堆更干净。

**生成时怎么调用和融入枝干**（以设定里生成力量体系为例）

1. 按槽位定主干（对应表待定，可用 [素材提取改造方案](素材提取改造方案.md) §6.4 作基础）。
2. 在主干下匹配枝：按上面「节点的标记和枝干匹配」做精确 / 大致匹配，带四道保险；作者也可以直接点选，或不选枝、整个主干都搜。这一步是「一句话有很多角度」的解法：把枝摆出来明确选。
3. 在枝的素材里检索：模型按灵感写一句需求，在这个枝的池里走现有的两路召回 + 融合 + 重排；枝里不到 10 条就全部列出。
4. 作者决定融入什么，三样分别可开关：
   - 枝的共性（共性摘要 + 常见变体）：给类型的框架，不带原作内容。
   - 具体素材（勾选的几条，带编号）：给具体的机制、代价、层级。
   - 第二个枝的共性：想融合两种体系时用。
5. 写进提示词，加在任务前面：【这类力量体系通常怎么运转】（枝的共性）+【可参考的素材】（现成的那一句）+【主次】。
6. 生成时要求标出每条借了哪条素材的哪一点；只参考了枝的共性的标「枝」。
7. 代码核对编号、列出没用上的素材、查原素材名字泄漏。采用后给被引用的素材和这个枝各记一次使用。

### 6.6 写法素材做成应用内可开关的 skill

把一条写法素材整理成一份可以随时挂上、随时撤掉的说明，写章节时生效。

- 好处：写法本来就是「怎么做」的知识；是引用不是复制，能干净撤掉；开着和关着各写一遍就能对比。
- **对 DeepSeek 有没有用**：有用，前提是应用负责把它拼进提示词。skill 本身只是一段文字，Claude Code 里的 skill 能用是因为 Claude Code 做了「列出说明 → 用到时读正文 → 放进对话」这三步。应用要自己实现这三步。Claude Code 里写的 skill（如 6.5）只在 Claude Code 里起作用。
- 要设计的：写某一章前只挑相关的几个注入，不能全塞；限制同时生效的数量，处理互相冲突；用架空版，避免带出原作例子；本地小模型遵守长说明的能力弱，一两条、每条一两句。
- 只适合写法、节奏、剧情套路。角色、势力、地点更适合做成资料卡或世界书条目。
- 用在大纲、写章节、润色，参数 · 灵感用不上。和检索是两条线。
- 和 [待办](待办.md)「每种 AI 润色配专门的提示词卡 + 资源」的关系：那里写的「不做成 skill」针对的是参数那一步的小帮手（单次调用）。这里说的是写章节时按需挂载的写法说明，和那一节的「文风库」是同一个方向，可以合并考虑。

### 6.7 向量怎么划分（2026-11-12，初稿）

分三层。属性名来自 [素材流程](素材流程.md) 的分类模板，素材里实际填了多少还没统计；写法、共鸣两类的属性名没有确认。

| 层 | 每个对象几个向量 | 文本由什么组成 | 怎么存 |
|---|---|---|---|
| 节点 | 每个主干、枝各 1 个 | 名称、别名、特征词、收录标准、共性摘要、什么时候会找它 | 单独一套，启动时加载 |
| 素材 · 整体 | 每条素材 1 个 | 现在的 `vectorText` 不变 | 一份统一的缓存，按文本内容存取 |
| 素材 · 分方向 | 最多 4 个，哪个方向有内容就建哪个 | 见下表 | 同上 |

作者问过要不要按枝把素材向量拆成独立的缓存。结论：节点向量单独一套可以；素材向量不按枝拆。理由：1.5 万条 512 维约 30 MB、比对是毫秒级，时间花在重排和查询编码上；一条素材挂多个枝会存多份；树一变文件要跟着搬；主干兜底和聚类都需要整个主干的向量。「只在某个枝里搜」靠筛选实现——`embedding.search` 只在传进去的条目里搜，Java 侧按挂载关系只传这个枝的素材，同时也省掉了现在每次把最多 2 万条检索文本发给 Python 的开销。素材涨到几十万条再考虑按主干分片或换专门的向量索引。（缓存「按文本哈希存取、按模型分目录」来自函数结构，加载细节没有逐行读。）

四个方向各收哪些字段：

| 分类 | 是什么 | 怎么运转 | 代价和限制 | 能起什么作用 |
|---|---|---|---|---|
| 世界观 / 体系 | 名称、细分类型、概括 | 规则内容、组成、层级与顺序、核心规则、对社会的影响 | 代价、限制、谁能打破 | 作者用法 |
| 物品功法 | 同上 | 作用、获取方式 | 代价、限制 | 作者用法 |
| 怪物 | 同上 + 外形 | 能力、习性、社会结构 | 弱点及原因 | 作者用法、与人类的关系 |
| 势力 | 同上 | 结构、资源、目标 | 内部矛盾 | 作者用法 |
| 地点 | 同上 + 特征 | 特殊规则、产出 | 危险 | 作者用法 |
| 角色 | 同上 + 人设核心、反差 | 动机、能力、关系 | （模板里没有） | 作者用法、名场面 |
| 情节 | 同上 | 起因、冲突、转折、结果 | （没有） | 功能 |
| 架空版 | 通用名、内核 | 内核、通用联动 | 一定保留 | 叙事用途 |

- 不进任何方向的向量：分类、量级、原素材 / 架空版、来源书（当筛选条件）；借用提示、换世界时替换、原作绑定（融入时给模型看）。架空版现在的检索文本带着后两项里的原作专名，拆方向后不再参与检索。
- 角色是硬套进四个方向的，要不要换成「人设 / 驱动 / 关系」待定。

哪件事用哪一层：

| 要做的事 | 拿什么比 |
|---|---|
| 匹配枝干 | 作者的话 ↔ 节点向量 |
| 建树时聚类分堆 | 素材的「是什么」向量之间（枝按类型分；整体向量混着用法和代价，会把类型冲淡） |
| 判断素材挂哪个枝（预筛） | 素材的「是什么」↔ 节点向量 |
| 枝内检索素材 | 需求句 ↔ 按生成内容选定的 1–2 个方向 |
| 方向是空的或都没命中 | 需求句 ↔ 整体向量（兜底） |
| 避免选出的几条太像 | 候选素材的「怎么运转」向量之间 |
| 入库比对、精炼合并 | 现在的做法不变 |

规矩：互相比较的两边用同一个向量模型；每个方向都同时用向量和关键词两路；多个方向的分数不加总不平均（分开列或取最高，并显示凭哪个方向命中）；先用固定对应选方向，记录作者的实际选择，攒够了再考虑自动调整。规模约 7 万个向量，1024 维约 300 MB，走 API 编码一遍约十几元。

依据（各搜了一轮，没读全文，都不是小说素材）：

| 案例 | 要点 |
|---|---|
| [Multi-Field Adaptive Retrieval](https://arxiv.org/abs/2410.20056v2)（微软，ICLR 2025，[代码](https://github.com/microsoft/multifield-adaptive-retrieval)） | 按字段拆开，各建向量和关键词索引，按查询判断哪个字段重要；分字段编码可胜过整篇编码，向量 + 关键词混用胜过单用 |
| [Multi-Aspect Dense Retrieval](https://research.google/pubs/multi-aspect-dense-retrieval/)（谷歌，KDD 2022）、[MURAL](https://arxiv.org/pdf/2312.02538)（WSDM 2024） | 商品搜索里每个面一个向量，好于单向量，更可解释；要训练，只借思路 |
| [CSFCube](https://arxiv.org/abs/2103.12906v2)（NeurIPS 2021） | 给一篇论文再指定一个面找相似的；当时的模型差距很大 |
| [LangChain MultiVectorRetriever](https://python.langchain.com/docs/how_to/multi_vector) | 一篇文档多个向量、命中任一个返回原文档，是通用工程做法 |
| [Four vectors, one record](https://www.craftedbydaniel.com/blog/four-vectors-one-record-how-i-split-embeddings-before-they-hit-search) | 简历的技能 / 经历 / 简介 / 整体四个向量；个人经验，无评测 |
| [arXiv 2601.11863](https://arxiv.org/html/2601.11863v1) | 不同字段的作用差别很大，有的帮助很小 |

动手前要确认：每个分类实际有哪些属性名、各填了多少；同一条素材的几个方向是不是真的不同（差不多就合并）；每个方向单独验证有没有用（第 7 节已安排）。

### 6.8 节点和叶子存什么、调用模型时的形式（2026-11-12，作者认可的草案）

**节点**（主干和枝同一种结构，主干 = 没有上级）：编号、上级；名称；收录标准；不收什么；共性摘要；常见变体；别名；特征词；什么时候会找它（每句记来源：AI / 作者 / 作者改选时记下的）；对应的生成槽位（只有主干有）；谁建的、状态（待确认 / 已确认 / 已忽略）；作者改过哪些字段（AI 不覆盖）；统计（成员数、被用次数、写摘要时的成员数）。中心向量放向量缓存，不放表里。

**叶子只存挂载关系**，不复制素材内容：节点编号、素材编号；谁挂的；状态（AI 建议 / 已确认 / 作者移走了——移走的要留着这一行，AI 才不会再挂回来）；依据的一句原文及其出处；匹配分；是否代表素材；在这个枝下被用过几次。素材的名称、概括、属性等每次从 `material` 表现读。架空版不单独挂，顺着 `source.originId` 找原素材所在的枝；合并过的素材挂主条目。存放：按规矩应是 Java 管的两张表，列表类字段用 JSON 列。

**调用模型时的形式**。原则：模型只看到短编号（N12、S1、行号），代码换回真实编号，对不上的丢掉；每种场合只给够用的字段并限长。

1. 树的概况（对话式 skill 每轮都带）：`[N12] 骑士力量体系（14）：收录标准`，按层缩进，只有名称、条数、收录标准。
2. 节点的检索文本（发给向量模型）：名称、别名、特征词、收录标准、共性摘要、什么时候会找它，各占一行。「不收什么」不放：向量模型不理解否定。
3. 归纳新枝时一条素材一行：`行号｜名称｜细分类型｜概括（≤60 字）`，行号是本次调用内的临时编号。
4. 判断归属（一次只问一个枝）：枝的名称、收录标准、不收什么、两条例子 + 素材的名称、细分类型、概括、属性（截到 300 字）→ `{"belongs": true, "evidence": "…"}`。「不收什么」在这里起作用。
5. 几个枝分数接近时让模型选：要生成什么 + 选定的灵感 + 候选枝 `[N12] 名称：收录标准。共性摘要前 80 字` → `{"pick": ["N12"], "why": "…"}`。
6. 生成时：【这类 X 通常怎么运转】（枝的共性摘要 + 常见变体）+【可参考的素材】。素材行沿用现成的两种写法：原素材用灵感墙的 `[S1]（来自《书》）（量级 N）[分类] 名称：…`，架空版用参数 · 灵感的 `[S2]【分类·架空版】通用名：内核。叙事用途…`。

### 6.9 什么时候建树（2026-11-12）

提取后建，入库时挂叶子，提取（逐章读）过程中不建。

- 不在逐章读时建：那时看到的是碎片，实体的事实要跨章攒、还要读第二遍；每章都多花 token；很多实体最后进不了素材库；会破坏「每步可单独重做」。
- 现在：用库里已有的素材建第一版。以后每本新书：在「素材选择」入库比对那一步顺带建议挂到哪个枝，作者一起确认。未归枝的攒够了再提议新枝。
- 入库时的建议有两种做法：并进整理卡片那次调用多输出一个字段，或入库时单独判断一次。倾向后者（树变了不用重新整理卡片），待定。
- 提取质量会影响树，这一点哪个时机都躲不开；但树能把问题暴露出来（哪个枝素材少、哪些挂不上、哪些缺字段），而且树和提取分开，提取改进后只更新叶子。
- 树反过来指导提取：用逐章读提示词里现成的「特别关注」（`chapter_prompt` 的 `focus`），哪个枝素材少，下一本书就写进去；或对已有的书用「重读这几章」。
- 用原素材建，架空版跟着走：所有素材都有原素材；原素材内容更具体；生成时同一条有架空版就优先给架空版；枝的共性摘要由模型去掉原作名字。

## 7. 检索测试计划（待执行）

### 7.1 要回答的问题

1. 现有检索在「故事方向 + 要生成的槽位」这种查询下，前 10 条里有几条有用？
2. 拆成多个检索方向分别检索，哪个方向在哪类槽位上有用？
3. 多个方向应该按槽位路由，还是全搜合并？
4. 入库时生成假设性问题再匹配，有没有提升？

### 7.2 约束

- 代码放 `python-service/lab/retrieval/`，用现有虚拟环境，不装新依赖。
- 只有 Java 打开数据库：素材经 Java 测试实例（8012）读一次存成快照，之后离线。不碰 8022 / 8021 / 5173 / 8001。
- 数据副本放 E 盘（C 盘快满），只复制 `nan_novel.db`。`DATA_DIR` 指向副本，向量缓存不写进日常的 `data/material-index/`。
- 大模型 key 只从环境变量或 `backend/application-secret.yml` 读，不打印、不写进结果。
- 复用：`python-service/scripts/retrieval_eval.py` 的 `fetch_materials` / `vector_text` / `variant_text` / `build_items` / `model_cfg` / `llm_json`；`app.local.embedding.search`（和产品同一套检索）。

### 7.3 步骤

0. **快照 + 覆盖率**（不调模型）：各分类条数；原素材 / 架空版 / 合并主条目各多少；全部属性键和出现次数；四个方向各有多少素材有内容；「细分类型」字段的取值分布；按来源书列出缺用途字段的条数。
1. **用例**：作者提供约 10 条，每条 = 方向 + 槽位 + 允许的分类。可以先给 3 条跑通。
2. **方案**：

   | 方案 | 查询 | 每条素材拿什么去匹配 |
   |---|---|---|
   | A 现状 | 方向原文 | 全部字段拼成一段 |
   | A2 | 槽位需求句 | 同 A |
   | V1–V4 | 槽位需求句 | 只用一个方向的文本，四个方向各跑一遍 |
   | R 路由 | 槽位需求句 | 按槽位选 1–2 个方向 |
   | F 全搜合并 | 槽位需求句 | 四个方向都搜，RRF 合并（对照组） |
   | C 假设性问题 | 槽位需求句 | 模型给每条素材写的 3 句问题，取最高分 |

   槽位需求句：每个用例调一次模型，「这个故事的 {槽位} 需要解决什么」，一句话，可手改。只有 C 需要调模型建索引，跑之前先报预计调用次数。
3. **盲标**：所有方案的前 10 条合并去重、打乱，不显示来自哪个方案；作者勾「有用」。
4. **统计**：每种方案前 10 / 前 5 里有用的平均条数；至少有 1 条有用的用例占比；只有某一种方案找到的有用素材单独列出；各方案的调用次数、token、耗时。

素材树的小规模验证可以一起做：抽 300 条素材、作者写 10 个主干、AI 归类，作者自己标 50 条看一致程度。

## 8. 还没定的

- 主干的完整清单，以及每个主干的收录标准。
- 「细分类型」字段和用途字段的覆盖率（第 7 节第 0 步）。覆盖率低的话要先补字段：做法同量级补全，每条素材调一次模型，根据已有的概括和属性补，不重读原文。
- 「每个灵感至少用上一条」要不要改成「合适才用」。强制引用会让「没用上」这个信号失真。
- 设定里素材怎么按槽位对口。可以直接参考 [素材提取改造方案](素材提取改造方案.md) §6.4 的表。
- 参数 · 灵感这一步到底要不要自动检索，还是改成手挑一两条当起点。
- 原素材写进自己的书时改到什么程度。现在只有提示词要求加标题级的专名检查。作者说先放着。
- 「有用」除了引用和对照，要不要再定几条代码能检查的标准。
- 入口表（[素材提取改造方案](素材提取改造方案.md) 第六节）是否作为产品实施的基础。
