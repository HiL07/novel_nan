## 一、背景与目标

**现状**（`python-service/app/material_facts.py`，详见 `docs/素材流程.md`）
- ① 提取 `scan`：原文按 3000 字一块（短于 1500 字的章节合并，长章节按段落切），每块一次调用，产出设定实体（world / faction / character / monster / location / item）和带 quote 的事实，quote 由代码核对；`rounds: 2` 时第二遍补新事实。另产出每块 ≤80 字的摘要，用作章节摘要。
- ② 整理卡片 `compile_cards`：实体 → 素材卡；同类世界观 ≥3 张合成体系卡；章节摘要每 20 章一窗，产出剧情段（plot）。
- 素材库：7 个分类平铺在一起。各个 AI 入口要不要用素材、用哪类，由各组件自己决定；自动规划的「你的想法 / 补充要求 / 生成故事灵感」完全不读素材库。

**问题**
1. 只记「设定」，不记「写法」：一章怎么开头、钩子怎么下、爽点怎么给、伏笔隔多久回收，这些都没有记录。
2. 剧情信息太薄：每块 80 字摘要撑不起剧情段，更撑不起全书结构分析。
3. 分章规则会把卷标题、正文里以「第X章」开头的句子当成章节；书头简介 ≥50 字就单独成一章。
4. 核对不过的事实只计数后丢弃，事后查不到、也恢复不了。
5. 素材入库后，各 AI 入口取用的规则不统一。

**参考**：EasyWriting（`E:\workplace\github\EasyWritting\easy-writing`）的拆书功能，借鉴点见附录 A。

**目标**
- 读原文的次数不增加：章节卡（写法）和设定实体在**同一次调用**里产出。
- 每本书得到一份「拆书档案」：章节卡、节奏统计、伏笔表、拆书报告，留在提取结果里，不进素材库。
- 素材库分 **设定 / 剧情 / 写法** 三层，新增「写法」分类（技法 + 配方），进库的只有提炼过、可复用的东西。
- 建立「AI 入口 → 素材层」的中央入口表，默认自动匹配、可以关掉；第一期接入自动规划。
- 不破坏旧数据：旧提取结果、旧素材、旧断点都能照常用。

**不做**：不改精炼合并算法；不改角色卡提取；不做 EasyWriting 的 Agent 对话、和作者自己作品的节奏对比（以后可以做）；第二期入口（写作、AI 构思、设定编辑器）这次只定接口，不接。

## 二、分章加固（`text_loader.split_chapters` + Java `ChapterCounter`）

### 2.1 现有规则（`app/text_loader.py:11–104`）
- `CHAPTER_RE`：`第[数字][章回节卷集部篇][^\n]{0,30}` / 「上部 xxx」/ `chapter N` / 特殊标题（序章、楔子、尾声…），整行匹配。
- 没有「第X章」时，用 `NUMBERED_RE`（`1.标题`、`一、标题`，不以句末标点结尾）兜底，至少 3 处才算。
- 首个标题前的文字 ≥50 字就成为「序/前言」章；只有标题、没有正文的跳过。
- Java `service/ChapterCounter` 的规则和它一致（文件管理页显示章数用），**两边必须同步改**。

### 2.2 改动（对照 EasyWriting 的 `reference-book.ts#detectHeading`）
| # | 规则 | 现在 | 改为 | 理由 |
|---|---|---|---|---|
| a | 卷 / 部 / 篇 / 集标题（`第X卷`、`卷X`） | 算一章 | **只断开，不算章**。卷标题和下一章之间的文字（卷简介）≥200 字时保留为一章，标题用卷名，否则丢掉；后面各章的 `volume` 字段记卷名 | 卷标题不是章，被算进去会多出空章和误摘要 |
| b | 像正文的假标题 | 只要求 ≤30 字 | 标题后半部分（编号之后）带「。」，或者**没有分隔符**（空格 / ：/ 、/ - / （ 等）就直接接「，；！？」时，不算标题 | 例：「第一次见面，他就……」 |
| c | 前缀 | 不支持 | 去掉「正文 / 正文卷 / VIP章节」前缀再匹配，标题里也去掉 | 下载站常见 |
| d | 书头 | ≥50 字成为「序/前言」 | **≥1500 字**成为「开篇」章；不到 1500 字的作为 `preface` 存进结果，不算章 | 书名、作者、简介不该被拿去抽素材 |
| e | 重复章名 | 空的那个被跳过（结果正确） | 保持不变，但不计入「空章」警告 | 下载站常把章名重复一行 |
| f | 超长章 | 由 `build_blocks` 切块 | 不变（分块负责切） | 分章只管识别标题 |
| g | 完全没识别到标题 | 整本当一章 | 按段落切成约 5000 字一段，标题「第 N 段」，并发警告 | 一整章会让章节卡没法用 |
| h | 警告 | 无 | 结果里加 `splitWarnings[]`：跳过了多少个空标题、超过 1/3 的章不到 200 字、按字数分了段 | 让用户知道分章可能不对 |

### 2.3 影响范围与兼容
- 调用方：`extractor.py`（提取两处）、`local/dataset.py`（训练按章分组）、`scripts/extract_eval.py`、爬虫产出的 txt（`crawl_site_selftest.py` 会验证）。
- **章节下标会变**：旧提取结果里存的是自己的章节列表，不重新分章，所以不受影响；提取中途的旧断点，指纹里有 `blocks` 数，分章变了块数就会变，断点作废重读。这是预期行为，在更新说明里写明。
- `ChapterCounter`：同样改，并对旧文件做一次重新计数（复用启动时的 `backfillChapterCounts`，加一个规则版本号标记，类似 `data/.defaults-applied`）。

### 2.4 验证
- 新脚本 `scripts/split_compare.py --files <txt…>`：打印新旧章数、前 20 个标题、新增 / 去掉的标题、警告。用 `data/upload/` 里的真实书（GBK / UTF-8、有卷 / 无卷、爬虫产出）各跑一本。
- Java 和 Python 章数一致：脚本调用 Java `/api/file/list` 拿 `chapter_count` 做比对。

## 三、提取：一次调用同时出实体和章节卡（`material_facts.scan`）

### 3.0 逐章串行提取（2026-11-02 定稿，替换原 §3.0 按章读 / §3.0.1 逐章查看 / §3.5 第 2 遍串伏笔）

用户要求一章一章提取、过程中能看见每一章。先核实了 EasyWriting 实际怎么做：

#### EasyWriting 实际逐章流程（核实结果）

两套拆书都是**真正一章一次调用、按顺序一章接一章**，界面上看到的逐章就是实际处理方式：

| | 旧「拆书工作台」 `src/utils/local-breakdown-engine.ts` | 2.0 Agent 拆书 `agent-runtime/indexer.py` + `src-tauri/src/agent_indexer.rs` / `agent_host.rs` |
|---|---|---|
| 粒度 | 每章一次调用，从不合并；正文最多 400 段（`CHAPTER_MAX_PROMPT_PARAGRAPHS`） | 每章一次调用（`extract(model, job)`），正文最多 4 万字（`TEXT_LIMIT`，超了截断并标 `truncated`）；导入时 >3 万字的章已切成 2 万字的「（续N）」 |
| 顺序 / 并发 | `for (const item of picked)` 串行，一章做完写一章 | 每轮领 4 章（参考书 `REFERENCE_BATCH`），轮内串行；一本书一条通道 |
| 上下文 | 只给本章（段落编号 `[n]`） | **滚动上下文**：上一章 oneLine（`previousOneLine`）、已出现过的人名表（≤120，按出现章数）、**未回收的伏笔**（≤40，带 threadId）——所以一遍就能把「回收」对到前面埋下的伏笔，不需要第二遍 |
| 落库 / 展示 | 每章写完立刻改状态 processing → done / failed，页面 2–3 秒轮询；点开一章：**左边原文按段落高亮**（outline 节点的 startPara–endPara），右边节点卡、节奏、设定、人物关系 | 每章写完立刻 `canon_put` + 发 `index_progress` 事件（带本章用量），界面进度卡逐章更新；失败的章记原因、继续下一章，连续失败 3 次放弃（可重置再试） |
| 暂停 / 续跑 | — | 暂停 / 取消 / 继续；已有有效章节卡的章不重拆 |

和我们的差别：我们现在为了速度**合并短章 + 并发读 + 读两遍**（第 2 遍补事实、串伏笔）。EasyWriting 用**串行 + 滚动上下文**换来一遍读完就能串伏笔、逐章即时可见，代价是大模型不能并发（我们大模型并发默认可开到 2–8；本地 GGUF 本来就是串行，没有损失）。

**用户已选（2026-11-02）**：① 串行 + 滚动上下文；② 每章一次，不合并短章；③ 查看时显示原文，并高亮 quote。
据此定稿如下。§3.3 / §3.4 / §3.6 / §3.7 里「块」的说法按本节理解为「一章（或超长章的一份）」；并发、第 2 遍串伏笔的内容以本节为准。

#### 定稿

##### A. 读取单位与顺序（`material_facts.build_blocks` → 改成 `chapter_jobs`）
- **一章 = 一次调用**，短章也不合并。分章就用第 1 步的 `split_book`；`kind: opening / volume / segment` 的条目也各算一章。
- 超长章才切开：上限 `maxChapterChars` = 大模型 20000 字、本地 / GGUF `chunkChars × 2`（默认 6000，受上下文窗口限制）。超过上限的章按段落切成几份，**按顺序读**（第 2 份起提示「这是《X》的第 k/n 部分」，并带上前一份的 oneLine），最后由代码合并成一章的章节卡（合并规则同原 §3.4）。
- **严格按章节顺序串行**：扫描阶段不再用 `concurrency`，大模型也一次只发一个请求。整理卡片 / 报告仍按配置并发。
- 速度预估（`ExtractOptionsDialog` 改估算）：调用次数 ≈ 章数 + 超长章的额外份数；时间按串行算（DeepSeek 一章约 10–20 s，一千章约 3–5 小时；GGUF 和现在差不多，本来就是串行）。界面要写明「逐章读，大模型不并发」。

##### B. 滚动上下文（每章的 prompt 里额外带的东西，都由代码挑）
| 内容 | 来源 | 上限 |
|---|---|---|
| 上一章 / 上一份的 oneLine | 上一条已完成的行 | 2 条 |
| 已知实体：本章原文里出现了名字 / 别名的 | `Book.known_in(本章原文)`（现在第 1 遍就能用，因为前面的章已经读完） | 15 个，每个带已知事实 ≤4 条 × 20 字 |
| 未回收的伏笔 / 悬念 / 承诺 | 代码维护的伏笔表 `T1…`，按最近埋下排序；再加上关键词出现在本章原文里的 | 20 条 |
- 任务说明相应改为：对已知实体只写**新的**事实；伏笔 `plant` 不写编号（代码分配 `T<n>`），`advance` / `payoff` 必须写列表里的编号 `id`。编号不在列表里的，按无关联的 payoff 记录（不丢）。
- 原来的「第 2 遍」不再承担串伏笔：`rounds` 默认改为 **1**；选 2 时，第 2 遍按同样的串行顺序，带全书已知实体再读一遍，只补漏掉的事实和实体（与现在一致，但不再输出章节卡 / 伏笔）。默认值等第 2 步实测后再定，对比的是「串行 1 遍」和「旧的并发 2 遍」的实体召回（§九）。

##### C. quote 位置（用于原文高亮）
- `Source.locate` 已经能给出 quote 在本块里的位置。改成记下**本章内的偏移** `at`（块内位置减去【标题】行的长度，再加上该份在章里的起点），写进每条事实 / 钩子 / 爽点 / 伏笔。
- 钩子也加可选的 `quote`（原文摘抄 ≤30 字），这样才能高亮；事件不要 quote。
- 模糊命中（trigram）的 `at` 只是近似位置：前端先在原文里精确查找 quote，找不到再用 `at` 附近高亮。

##### D. 断点（每章一行）
- `pass1.jsonl` 的 key = 章下标 `ci`（超长章 = `ci:part`）。行内容：`{ci, part, title, entities, card, threadOps, ok, bad, unverified, usage, at}`。续跑时**按顺序重放**这些行，重建 `Book`、伏笔表和上一章 oneLine，然后从第一个没完成的章接着读。
- 指纹加上 `mode: serial-v1`、`cards`、`maxChapterChars`；旧的并发断点会作废重读。
- 某章失败：记一行 `{ci, failed: true, error}`，继续下一章（这一章的滚动上下文就缺这一章）。整本读完后，失败的章自动再试 1 次；仍失败的留给「重读这几章」。连续失败 5 章就停下，任务转 INTERRUPTED（和现在网络错误的处理一致）。

##### E. 逐章查看（替换原 §3.0.1）
- Python `GET /api/extract/checkpoints/{key}/chapters?since=N` → `{total, current (正在读的 ci), chapters: [{ci, title, kind, status: pending|reading|done|failed, card, entities: [{category, name, facts: [{fact, quote, at, verified}]}], unverified, threadOps, error}], next}`。`since` = 已经拿到的行数，增量返回。
- Python `POST /api/extract/chapter-text {fileId, fileExt, ci}` → `{title, text}`：照提取时的流程重新解码、分章（`text_loader.to_plain_text` + `split_book`），缓存最近 2 个文件；超长章返回整章。
- Java：`GET /api/novel/extract/{id}/live?since=N`（QUEUED / RUNNING / INTERRUPTED 读断点；SUCCEEDED 读结果文件里的 `chapterCards` + 实体事实，按章整理成同样的形状）；`GET /api/novel/extract/{id}/chapters/{ci}/text`（用任务的 fileId / ext 转发给 Python）。
- 前端 `components/material/ExtractLive.vue`（提取中点「查看」打开；提取成功后是结果抽屉里「拆书」页签的「逐章」视图）：
  - 左：章节列表，状态点为 待读 / 读取中（转圈）/ 完成 / 失败，每章后面有爽点数、章末钩子标记、新实体数；默认跟随最新读完的章（可关）；运行中每 3 秒按 `since` 拉一次。
  - 中：本章原文（按段落显示，长章分页），quote 处浅色底高亮，颜色按类别（钩子 / 爽点 / 伏笔 / 事实）区分。
  - 右：本章卡（一句话、事件、钩子、爽点、伏笔 埋 / 推 / 收 + 编号、情绪三段），以及本章新发现的实体和事实（未核实的灰色）。点任意一条，原文就滚到它的 quote 处并高亮；点原文里的高亮，右边对应条目也会高亮。
- 「重读这几章」（`POST /api/novel/extract/{id}/reread {chapters}`）仍放到第 4 步之后。

##### F. 实施顺序调整（第八节第 2 步改为）
2a. `chapter_jobs` + 串行读 + 滚动上下文 + 章节卡 prompt / 解析 / 合并 + quote 偏移 + 每章断点 + 结果字段 + `pacing`；
2b. 逐章查看接口（Python 两个 + Java 两个）+ `ExtractLive.vue`；
2c. 在 GGUF 4B 和 DeepSeek 上，用 `scripts/extract_eval.py` 对比「串行 1 遍」和「旧并发 2 遍」，再定 `rounds` 的默认值。原 §3.5（第 2 遍串伏笔）作废。

### 3.0.2 每章提取哪些内容（2026-11-02 定稿；§3.1 的 `cards` 开关由这里的三档 `depth` 代替，§3.2 的字段以这里为准补充）

原则：**每一项都要有去处**（下游谁用），能用代码算的不让模型写；每多一项，模型每章就多输出约 50–200 token（GGUF 4B 输出慢，格式出错的风险也更高）。

| 组 | 项 | 写什么 | 下游去处 | 每章输出 | 模型可靠性 | 建议 |
|---|---|---|---|---|---|---|
| 设定 | 设定实体 + 事实（现有） | 世界观 / 势力 / 角色 / 怪物 / 地点 / 物品功法，每条事实带原文 | 整理卡片 → 素材库设定层 | 200–600 | 高（原文核对） | 必选 |
| 剧情 | 一句话 oneLine | 本章发生什么、起什么作用 | 章节摘要、剧情段、拆书报告、逐章列表 | 30 | 高 | 必选 |
| 剧情 | 关键事件 3–6 条 | 推动剧情的事件 | 剧情段、报告、案例检索 | 80–150 | 高 | 必选 |
| 写法 | 钩子（开头 / 章中 / 章末 × 类型 × 强度 + 原文） | 怎么吊读者 | 节奏统计、写法素材、案例 | 60–120 | 中 | 必选 |
| 写法 | 爽点（类型 × 强度 × 旁观者反应 × 铺垫 + 原文） | 兑现了什么满足感 | 节奏统计（爽点密度 / 最长空窗）、写法素材 | 60–150 | 中 | 必选 |
| 写法 | 伏笔 / 悬念 / 承诺（埋 / 推 / 收 + 编号） | 线索的开合 | 伏笔表、平均回收距离、报告 | 40–120 | 中（靠滚动上下文） | 必选 |
| 写法 | 情绪曲线（开头 / 高潮 / 结尾） | 读者情绪起伏 | 报告、逐章查看 | 20 | 中 | 推荐 |
| 写法 | 本章功能（铺垫 / 过渡 / 冲突升级 / 高潮 / 收尾 / 日常 / 揭秘 …，单选） | 这一章在节奏里的角色 | 节奏曲线分段、配方 | 5 | 高 | 推荐（便宜） |
| 人物 | 主角变化（实力 / 境界、金手指、物品得失、地位 / 身份、目标）+ 原文 | 主角这章怎么变了 | 阶段表（第几章到什么实力）、力量体系阶梯、全书骨架配方、量级判断 | 30–100 | 中 | 推荐 |
| 人物 | 出场人物 + 关系变化（谁和谁：结盟 / 反目 / 师徒 / 暧昧 …） | 人物网络怎么变 | 角色素材（关系）、世界书人物局面的参考、报告「主角怎么立住」 | 40–120 | 中 | 推荐 |
| 人物 | 名场面 / 金句（人物原话，≤3 句，带说话人） | 有辨识度的台词 | 角色卡原型的台词证据、写法案例 | 40–90 | 高（原文核对） | 可选 |
| 深拆 | 情节节点（3–6 个，带原文区间：开头句 – 结尾句） | 本章内部的起承转合，原文按节点分段着色（EasyWriting 旧工作台那种） | 逐章查看的原文分段、写法学习 | 150–300 | 中低（小模型区间常错） | 可选 / 只给大模型 |
| 深拆 | 黄金三章深拆（只前 3 章：前 300 字钩子、主角人设怎么立住、核心困境、2–3 句原文点评） | 开篇写法 | 报告「开篇怎么写」、开篇配方 | 只 3 章，各 200–300 | 中 | 推荐（只 3 章，几乎不花钱） |
| 深拆 | 倒叙 / 误导标记（事件是回忆、伪装、假死） | 叙事技巧 | 报告 | 10 | 中低 | 不做（收益小） |
| 代码算 | 字数、段落数、平均段长、对白比例、出场人物（按已知实体名在原文出现）、新实体数 | — | 统计、逐章列表 | 0 | 准 | 必做（免费） |

#### 用户决定
- 人物：主角变化、出场人物 + 关系变化、名场面 / 金句全要；另加「**物品 / 怪物之类**」= 每章的**设定动态**（下表）。
- 写法：情绪曲线 + 本章功能、黄金三章深拆、情节节点（原文分段）全要。不做倒叙 / 误导标记。
- 做成**三档**，在提取选项里选；钩子 / 爽点类型表**就用 EasyWriting 那套**，表外的值丢掉。

#### 三档的内容
| 档 | 每章内容 | 适合 |
|---|---|---|
| **快速** | 设定实体 + 事实；一句话；关键事件；代码统计 | 只想要素材库设定，最省 |
| **标准**（默认） | 快速 + 钩子、爽点、伏笔（埋 / 推 / 收）、情绪曲线、本章功能、主角变化、出场人物关系变化、设定动态、名场面金句；前 3 章另加黄金三章深拆 | 拆写法、做报告 |
| **深拆** | 标准 + 情节节点（3–6 个，原文分段着色） | 想逐章精读；建议用大模型，GGUF 4B 会提示「节点区间可能不准」 |

档位存在 `materials.depth: fast|standard|deep`（替代 §3.1 的 `cards` 开关：`fast` = 不出章节卡）。断点指纹带上档位。估算按档位给出每章输出 token、时间和费用。

#### 新增字段的格式（追加到 §3.2 的 `chapters[]` 每项里；字段按这个顺序写，截断时先丢后面的）
```
"function":"铺垫|过渡|冲突升级|高潮|转折|揭秘|日常|收尾",                // 单选
"emotion":{"open":"≤8字","peak":"≤8字","close":"≤8字"},
"lead":"主角名（第一次判断后由代码记住，后面各章放进滚动上下文）",
"leadChanges":[{"field":"实力|金手指|物品|地位|目标|其他","before":"可空","after":"≤30字","quote":"原文"}],
"relations":[{"a":"人物","b":"人物","rel":"结盟|反目|师徒|亲属|暧昧|主从|敌对|其他","change":"新建|加深|破裂|揭示","text":"≤30字","quote":"原文"}],
"entityMoves":[{"name":"实体名","category":"item|monster|location|faction|world|character","act":"首次登场|获得|使用|击败|失去|揭示","text":"≤30字","quote":"原文"}],
"lines":[{"speaker":"说话人","quote":"人物原话 ≤40字"}],                   // ≤3 句，必须逐字出自原文，否则丢掉
"golden":{"hook300":"…","establish":"…","dilemma":"…","anchors":[{"quote":"原文 ≤40字","comment":"≤40字"}]},  // 只在前 3 章（kind = chapter 的前三个）要求
"nodes":[{"title":"4–8字","from":段号,"to":段号,"text":"做了什么、为什么有效 ≤60字","hot":true/false}]  // 只在深拆档；正文按段落编号 [n] 给模型
```
- 核对：`leadChanges` / `relations` / `entityMoves` 的 quote 照 §3.3 核对，对不上就清空 quote、标 `verified:false`（条目保留）；`lines` 必须核对通过，否则丢掉；`nodes` 的段号截到 1..段落数，区间按顺序、不重叠（代码修正），只在深拆档给段落编号。
- 代码算（不花 token）：字数、段落数、平均段长、对白比例、**本章出现的已知实体**（名字 / 别名在原文出现：人物、物品、怪物、地点…都算）、新实体数。设定动态和代码算的出现列表互补：后者告诉你谁出现了，前者告诉你出现时发生了什么。
- 滚动上下文（§定稿 B）加一行：主角名 + 主角当前状态（最近的 `leadChanges` 各字段最新值）。
- token 预算（初值，2c 实测后调）：快速 API 1500 / 本地 1000；标准 API 3000 / 本地 2000；深拆 API 3600 / 本地 2400。

#### 这些数据的去处
- `leadChanges` → 节奏统计里加「主角成长线」（第几章到什么实力 / 拿到什么），报告「阶段划分」「主角怎么立住」的输入，写法配方的位置依据；以后可以喂给自动规划的阶段表。
- `relations` → 整理卡片时并进角色实体的「关系」属性（只取核对过的），报告用。
- `entityMoves` → 整理卡片时给对应实体补「首次登场章」「关键事件」，素材卡的 `bookPos` 更准；逐章查看里显示为「本章设定动态」。
- `lines` → 角色卡原型提取的台词证据（`persona` 的 seedFacts），写法案例。
- `golden` → 报告「开篇怎么写」、开篇配方。
- `nodes` → 逐章查看的原文分段着色；报告的 keyBeats 参考。
- `function` / `emotion` → 节奏曲线分段、报告。

### 3.1 开关
`MaterialOptions` 新增 `cards: bool = True`（「同时拆写法」）。关掉后输出和现在完全一样。`ExtractOptionsDialog` 加开关，时间估算按 3.6 的新 token 预算算。

### 3.2 第 1 遍的 prompt（在 `scan_prompt` 上增量修改）
不再要求块级 `summary`，改为要求 `chapters`：**块里每个【标题】一条**（块内合并了几个短章就有几条，长章被切开的块只有一条）。

```
"chapters":[{
  "title":"块内【】里的标题，原样",
  "oneLine":"本章发生了什么、起什么作用，≤40字",
  "events":["关键事件，≤30字", …3–6 条],
  "hooks":[{"pos":"open|mid|end","type":"悬念|危机|反转|期待|情绪|信息|关系","text":"≤30字","strength":1-3,"quote":"原文摘抄 ≤30字，可空"}],
  "payoffs":[{"type":"打脸|装逼|升级|收获|认可|逆袭|报复|掌控|越级|情感|团宠","strength":1-3,
              "amplified":true/false,"setup":"铺垫来源，可空","quote":"原文摘抄 ≤30字"}],
  "threads":[{"act":"plant|advance|payoff","id":"T3（advance / payoff 时写给定列表里的编号，plant 不写）","kind":"伏笔|悬念|承诺","text":"≤30字","quote":"原文摘抄 ≤30字"}],
  "emotion":{"open":"≤8字","peak":"≤8字","close":"≤8字"}
}]
```
规则（追加在 `SCAN_RULES` 后面，写成编号条目）：
- 钩子：open = 开头几段吊胃口的；end = 章末留给下一章的；mid 是章中的，可选；没有就留空数组。
- 爽点：本章兑现给读者的满足感；`amplified` = 写了旁观者的震惊 / 议论；`setup` 写它靠什么铺垫。
- 伏笔：plant = 新埋的；payoff = 本章明确回收了前文的。只写正文明确写出的，不猜。
- 枚举只能用给定的值；不确定就不写这一条。

**为什么不分两次调用**：本地 GGUF 读原文约 16 s / 千字（`docs/素材流程.md`），主要花在 prompt 处理上；只多输出几百 token，比再读一遍原文便宜得多。风险是输出变长后小模型更容易出格式错，见 3.6 和 3.8。

### 3.3 解析与核对（`parse_scan` 旁边新增 `parse_cards`）
- 标题对应：把模型给的 `title` 规范化（`_norm_title`）后，和块里各个【标题】比对；对不上时按条目顺序依次对应块里的章节；条数多于章节数时，多出来的丢掉。
- 枚举校验：`type` / `pos` / `act` / `kind` 不在白名单的那一项丢掉；`strength` 超出 1–3 时截到边界。白名单常量 `HOOK_TYPES`、`PAYOFF_TYPES`、`THREAD_KINDS` 放在 `material_facts.py` 开头。
- quote 核对：payoffs / threads 的 quote 用现有的 `Source.locate` 核对。**对不上时不删条目**：清空 quote、标 `verified: false`（写法判断本身仍有参考价值，只是没有原文证据），计入 `factStats.cardQuotesUnverified`。
- 长度截断：各文本字段按上面的字数上限 ×2 截断，防止模型写成长段。

### 3.4 跨块合并（新类 `ChapterCards`，和 `Book` 并列）
一个长章节被切成几块时，每块各给一条，由代码合并：
- `events` / `payoffs` / `threads`：按块的顺序拼接；events 最多保留 8 条（优先保留每块的第一条，保证覆盖到）。
- `hooks`：open 钩子只取第一块的，end 钩子只取最后一块的，mid 全部保留（≤3）。
- `oneLine`：只有一块就用它；多块时把各块的 oneLine 用「；」连起来，截到 80 字。
- `emotion`：open 取第一块的，close 取最后一块的，peak 取 payoff 强度最高那块的 peak（都没有就取中间那块）。
- 合并在内存里完成；断点里存的是**每块的原始 cards**（3.7），所以续跑、重算都是确定的。

### 3.5 第 2 遍串伏笔（作废）

改为串行读时用滚动上下文直接串伏笔，见 §3.0 定稿 B。

- 块大小、并发都不变。

## 四、整理：拆书档案 + 写法素材（新模块 `app/breakdown.py`，由 `compile_cards` 调用）

### 4.1 节奏统计 `breakdown.pacing(chapterCards, threads, text)`（纯代码，提取结束时就算）
```
{chapters, carded,                       // 总章数、有章节卡的章数
 payoffsPerChapter, endHookRate,          // 每章平均爽点数、章末钩子章数 / 有卡章数
 longestPayoffGap{length, from, to},      // 连续无爽点的最长区间（沿完整章节序，没卡的章会打断区间）
 hookTypes[{type,count}], endHookTypes[], payoffTypes[],
 amplifiedRate,                           // 写了旁观者反应的爽点占比
 threads{planted, paid, avgDistance|null},
 opening[{ci, title, oneLine, hooks, payoffs}] (前 3 章),
 curve[{ci, payoffPeak, payoffCount, endHook}] ,
 style{avgParagraph, dialogRatio}}        // dialogRatio 复用 extractor.dialog_ratio
```
算法照搬 EasyWriting `agent_breakdown.rs#summarize`（附录 A.4）。

### 4.2 拆书报告（`compile` 新选项 `report`，默认开；需要提取结果里有 `chapterCards`）
**输入**：Java 从结果文件读出 `chapterCards` + `pacing` + `threads`，和 `entities` / `chapters` 一起发给 Python（`MaterialCompileService` 组装请求时加这三个字段；`POST /api/extract/compile/jobs` 的请求模型加这三个可选字段）。

**分段归纳**（map）：每章压成摘要 `{no, title, oneLine, events≤4, hooks, payoffs(type/strength/amplified), planted, paid, emotion}`；按 ≤40 章、≤12k 字分段；每段一次调用（`_parallel`，并发 = 配置的 concurrency）：
```
{"stage":"阶段名","goal":"主角目标与读者期待",
 "keyBeats":[{"ch":章号,"what":"发生了什么","technique":"用了什么写法、为什么有效"}],   // 3–6
 "pacing":"爽点与钩子的规律，引用章号","characterMoments":["主角靠什么立住，带章号"],
 "threads":["埋下 / 回收的伏笔，带章号"]}
```
**合并**（reduce，一次调用）：输入 = 各段归纳结果 + `pacing` + 开篇 3 章摘要 + 覆盖范围（缺卡的章）：
```
{"overview":"这本书靠什么抓住读者",
 "stages":[{"range":"第1–40章","title","goal","payoff"}],
 "opening":"开篇几章各完成什么任务","characterEstablishment":"主角怎么立住，带章号",
 "pacing":"节奏规律，引用统计和章号","threads":"伏笔与信息释放",
 "techniques":[{"name":"写法名","how":"作者能照着学的要点","when":"适用位置：开篇/高潮/过渡/章末…","chapters":[章号]}],  // 3–8
 "recipe":[{"position":"第1章 / 第4–10章","tasks":"写法任务，只用主角/对手/配角等角色位置"}],
 "caveats":["覆盖范围与数据不足"]}
```
- 规则（照 EasyWriting `REPORT_RULES`）：结论要能对到章号；只依据给定数据；recipe 不写原书人名、地名和具体情节；没拆的章节不补配方。
- 校验：章号超出范围的去掉；`techniques` 少于 1 条，或 `stages` 为空时，重试一次（同一 prompt），还不行就只保存统计，报告记 `error`。
- 断点阶段：`segments`（每段一行）、`report`。
- 本地小模型：分段改成 ≤20 章 / 6k 字，合并时只带各段的 stage / keyBeats / pacing。

### 4.3 写法素材（新分类 `technique`，见第五节）
- 每条 `techniques` 生成一个候选：`title` = 写法名，`subtype` = 写法名的类别（模型给；没给就用 `when`），`summary` = how 的第一句，`detail` = how 全文，属性：`做法`（how）/ `适用位置`（when）/ `为什么有效`（从相关段的 keyBeats.technique 里挑同一章的）/ `原文案例`。
- **原文案例**（代码挑）：从这条写法引用的章节里，选 strength 最高、已核实的 payoff / hook quote，≤3 条，格式「《书》第N章：quote」。没有核实过的 quote 就不写这个属性。
- `recipe` 整份作为一个候选：`subtype: 配方`，`title` = 「《书》式开篇配方」这类（不含人名），属性 = 各个 position → tasks。
- `candidateId` = sha1(`technique:` + 规范化写法名)；同一本书重新整理时，按现有 `createCandidates` 的同书同名去重规则跳过重复。
- `tier` 留空；`bookPos` = 第一个引用章节 / 章数。

### 4.4 防原书人名（剧情段和写法共用）
- 名单 = character 实体里事实分布在 ≥2 章的 name + aliases（只拆了 ≤2 章时 ≥1 章就算），减去称谓表（照搬 EasyWriting 的 `COMMON_TITLES`，放进 `breakdown.py`），并去掉单字。
- 检查 technique 候选的 title / summary / detail / 属性值、recipe 的每一步、剧情段的各个字段：命中时把命中的名字列出来，让模型「换成角色位置」重写**一次**；还命中就保留，但候选上带 `leaks: [名字]`，候选箱里标红提示（入库仍需人工确认，不自动拦）。

### 4.5 剧情段换输入
`arc_prompt` 每行由「标题：摘要」改为「标题：oneLine｜爽点：类型(强度)｜章末：钩子类型」（有章节卡时）；没有章节卡时照旧。窗口大小、去重规则不变。

### 4.6 报告的存放
- Python compile 结果多返回 `report`（含 pacing 副本和 render 好的 markdown 文本）；Java 写到 `data/extract-results/<extractId>.report.json`（复用 `ExtractResultStore` 的写法：临时文件 → fsync → 原子改名 → SHA-256），`material_compile` 加列 `report_path`（`sql/material_compile.sql` + `init.sql` + `SchemaMigrations`）。
- `GET /api/novel/extract/{id}/report` → 最近一次成功生成报告的整理任务的报告；没有就返回 `null`。
- 不入库、不进向量检索。

### 5.1 层和分类
| 层 `layer` | 分类 | 名字规则 | 主要去处 |
|---|---|---|---|
| `setting` 设定 | world / faction / character / monster / location / item | 可以带原书名字 | 设定编辑器、自动规划的设定步骤 |

## 十、风险与应对

| 风险 | 应对 |
